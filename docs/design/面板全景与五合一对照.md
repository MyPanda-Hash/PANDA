## 3. 五条主流程的现状对照

### 3.1 P2P 采购到付款

```text
请购单[PU_REQ] ─→ 采购订单[PU_ORDER] ─→ 到货单[ARRIVAL_IN]
                        │                       ↓
                        │                检验单[INSPECTION]
                        │                       ↓ 放行
                        └──── 直接入库 ──→ 采购入库单[PURCHASE_IN] ✅库存+应付
                                                ↓
                                       采购发票[PU_INVOICE] ✅应付
                                                              ↓
                                              应付单[finance_voucher AP] ✅已落库
                                                              ↓ ✅已实现
                                              付款单[RECEIPT_PAYABLE] ✅ → 核销 ✅
```

状态：**P2P 全链闭环**。零收料/零质检时采购订单可直接生成采购入库单（`直接入库` 支线），
同一订单行与到货链互斥：已有到货单的订单行不能再直入。退货方向：采购退货单 `CT-` 产生
`AP_RETURN` 冲减应付。

### 3.2 O2C 订单到收款

```text
报价单[QUOTE_ORDER] ─→ 销售订单[SO_ORDER] ─→ 生产加工单[MANU_ORDER]
                                                      ↓
                                            产成品入库单[FINISH_IN] ✅库存+应付
                                                      ↓ ✅生单已实现
                                              销货单[SALE_INV] ✅可生成
                                                      ↓
                                            销售出库单[SALE_OUT] ✅库存+应收
                                                      ↓
                                            销售发票[SALE_INVOICE] ✅应收
                                                      ↓
                                              应收单[finance_voucher AR] ✅已落库
                                                      ↓ ✅已实现
                                              收款单[RECEIPT] ✅ → 核销 ✅
```

状态：**O2C 全链闭环**。活体验证：`XS-2026-11-0201`（生单）、`CK-2026-11-0203`（AR 250.00）、
`SK-2026-11-0201`（收款 200 核销，AR 转「部分结算」）。

### 3.3 P2M 计划到制造

```text
销售订单 ─→ MPS 主生产计划 ✅ ─→ MRP 物料需求运算 ✅ ─→ 齐套分析 ✅
                              ↓
                     采购建议 / 自制建议 ✅
                              ↓
                     生产加工单[MANU_ORDER] ✅
                              ↓
                     工序派工单[DISPATCH] ✅
                              ↓
                     工序汇报单[PROCESS_REPORT] ✅
                              ↓
                     工序报检单[PROCESS_INSPECT_APPLY] ✅
                              ↓
                     生产过程检验单[PROCESS_INSPECTION] ✅
                              ↓
                     产成品入库单[FINISH_IN] ✅已落库存
```

状态：**计划链与执行链均已打通**。活体验证：7 个产品进入 MPS，BOM 三层递归展开成 12 条物料需求，
齐套分析 13 行明细可定位到具体缺料子件。

### 3.4 W2W 仓内作业

```text
入库指令 ─→ 采购入库[PURCHASE_IN] ✅ / 产成品入库[FINISH_IN] ✅
                    ↓
              库存余额表[stock_balance] ✅
                    ↓
库内：调拨单[TRANSFER] ✅ / 库存盘点单[STOCK_CHECK] ✅ / 货位调整单[LOCATION_ADJUST] ✅
                    ↓
出库指令 ─→ 销售出库[SALE_OUT] ✅ / 材料出库[MATERIAL_OUT] ✅ / 其他出库[OTHER_OUT] ✅
```

状态：**单据层通，余额表已上线，拣货作业已实现；缺复核与上架作业。**

### 3.5 Q2Q 质量贯穿

```text
到货单 → 检验单 → 放行 → 采购入库  ✅ 全通
加工单 → 首件报检 → 检验        ✅ 全通
工序汇报 → 工序报检 → 过程检验   ✅ 全通
产成品 → 成品报检 → 检验       ✅ 全通
追溯：正向 / 反向               ✅ 全通
```

状态：**端到端完整，且已升级为三态判定 + SPC 管控。缺不良处置单与实物控制图渲染。**

**关键设计**：退货方向由 `StockTxnService` 的方向表决定，不靠单据名推断。

## 16. 报检数量校验与单据直达（2026-11-02）

### 16.1 用户发现的真实缺陷

反馈："怎么在还在生产中就已经报检完成了呢？数量对的上吗？"

核查结果——**确实对不上**：

| 项 | 数据 |
|---|---|
| `MO-2026-08-0009` 状态 | **生产中** |
| CP001 计划 / 累计完工 | 200 / **160** |
| CP002 计划 / 累计完工 | 100 / **0** |
| `BJ-2026-08-0001` 报检合计 | **350** |

两处矛盾：
1. 报检 350 > 累计完工 160 —— 未生产的货被报检了
2. `CP004` 减速箱体 50 件**根本不在**该加工单的产品明细里（该单只有 CP001 / CP002）

根因：`validateQualityForApproval()` 只校验行内数量守恒（合格+不合格=检验数量），
**没有校验报检量是否超过上游累计完工量，也没校验报检产品是否属于该加工单**。

### 16.2 修复：新增上游对齐校验

`PxService.validateReportAgainstUpstream()`：

| 校验 | 规则 | 错误信息 |
|---|---|---|
| 产品归属 | 报检的存货编码必须在加工单 `products` 明细里 | `报检的产品 CP004 不在加工单 MO-xxx 的产品明细里` |
| 数量上限 | 同一产品多行合计 ≤ 该产品 `累计汇报套数(工序单位)` | `报检数量 999 超过加工单 MO-xxx 的累计完工量 160，请先完成报工再报检` |

### 17.7 工序报检补产品归属校验（2026-11-02 补）

- 汇报单**没填产品编码**时跳过该校验（无从比对，不能凭空判定非法），

### 17.9 报工量为 0 的专门提示（2026-11-02 补）

§17.8 的第二条已补上，但落点不在审核、在**保存**。

**为什么不在审核**：报检单引用报工量为 0 的工序时，`validateSourceLinks` 在保存阶段就先拦下了，
给出的是笼统的 `来源明细超量：GX-xxx 第 1 行，可执行 0.0，已占用 0.0，本次 10.0`。
用户看不出"可执行 0.0"是因为工序还没报工。审核阶段的提示（`尚未报工`）反而很难走到：
汇报单一旦被下游单据引用就不许弃审，报工量改不下去。

**改法**：在 `validateSourceLinks` 的超量判断里加一条来源行分类 —— 来源面板是 `PROCESS_REPORT`
且该行 `报工数量` 为 0 时，换成人话提示；其余来源仍走通用超量提示。

| 场景 | 提示 |
|---|---|
| 工序报工量 0 | `工序 PX001 下料 尚未报工（工序汇报单 GX-2026-11-0203 第 1 行报工数量为 0），请先报工再报检` |
| 其余来源超量 | 保持 `来源明细超量：… 可执行 / 已占用 / 本次` |

两处并存：保存阶段走来源行分类（主路径），审核阶段还会再过一遍工序比对（兜底）。

**顺带**：`GlobalExceptionHandler` 的兜底分支现在会 `log.error` 记录堆栈，
返回客户端的文案不变（仍是"服务器内部错误"，不回显内部细节）——否则 500 只能靠猜。

按 TDD：先写 2 个测试（报工 0 → 要有专门提示、报工正常/非工序来源 → 不套用该提示），
确认红（方法不存在），补 `unReportedProcessMessage` 后转绿。

## 20. 补模块 + 表格对齐（2026-11-02 深夜）

### 20.1 权限矩阵表头与表体不对齐

现象：表头复选框比表体复选框右移，列间距也不一致。

原因：表头单元格里塞「复选框 + 文字」，内容比 60px 的列宽还宽，`table-layout` 是 auto，

按 PDA 常用作业逐张建单 → 审批（`_scratch/e2e-warehouse/e2e_pda_flow.py`，admin，2026-11-12）：

| 单据 | 建单/审批 | 库存事务 | 结论 |
|---|---|---|---|
| 其他入库单 `OTHE-20261112-001` | 通过 | 原料仓 +5 | 正常 |
| 其他出库单 `OTHE-20261112-002` | 通过 | 原料仓 −1 | 正常 |
| 调拨单 `DB-20261112-001` | 通过 | **0 条** | 调出仓没减、调入仓没加 |
| 库存盘点单 `PD-20261112-001` | 通过 | **0 条** | 盈亏不调账 |
| 货位调整单 `HW-20261112-001` | 通过 | **0 条** | 货位不落账 |

根因：`StockTxnService#post/reverse` 用 `directionOf(panelCode)` 当闸门，只有单方向出入库面板
能落账；调拨是「一出一进」没有单一方向，`buildTransferTxns` 虽然写好了却永远走不到，
审核直接返回 0。盘点/货位调整根本没有折算逻辑。

### 25.2 修复后的落账口径（用户拍板：审核直接调账）

| 单据 | 审核后落的事务 | 说明 |
|---|---|---|
| 调拨单 `TRANSFER` | 每行两条：调出仓 OUT + 调入仓 IN | 结存总量不变，仓间搬货 |
| 库存盘点单 `STOCK_CHECK` | 按「盈亏数量」一条：盘盈 IN / 盘亏 OUT | 缺盈亏列时按 实盘 − 账面 兜底；金额取结存均价 |
| 货位调整单 `LOCATION_ADJUST` | 每行两条：原货位 OUT + 新货位 IN | 数量/仓库不变只换货位；原货位有值时先校验可用量 |

`postsStock()` 统一回答「这张面板审核后要不要落库存」，`post/reverse` 都走它；弃审按面板+单号冲销。

## 26. 主生产计划（MPS）与物料需求汇总（MRP）（2026-11-12）

### 26.1 为什么恢复 MPS（而不是再造一个空面板）

2026-11-09 把 `MPS_PLAN` / `MRP_RESULT` / `KIT_ANALYSIS` 三个横向汇总**报表**下线，能力并入
「计划分析」单页——但计划分析只有「按单」视角：一张订单一张单地看，**没有计划期**，
多张订单无法一起排，也看不出某个月总共缺多少料。这次恢复的是**单据**形态的 MPS：
表头带计划期，明细是成品行 + 计划数量 + 开工/完工日期 + 来源订单行，纵向衔接销售订单、
横向给 MRP 用。`MRP_RESULT`、`KIT_ANALYSIS` 仍然不造面板。

### 26.2 实现

| 层 | 内容 |
|---|---|
| 面板 | `MPS_PLAN` 由「报表占位」升级为**单据**（`MpsPanelRegistry` 启动时幂等升级，占位面板才覆盖，真单据只补不盖） |
| 生成 | `POST /api/px/mps/generate {计划期}`：已审核销售订单 × 未计划量 → 计划行。已计划量按「来源销售订单 + 行号」累计，**重复生成不翻倍**；同一计划期只维护一张草稿计划 |
| MRP | `POST /api/px/mps/mrp {编号}`：逐来源订单走计划分析（BOM 展开 + 库存扣减），再按物料编码**横向汇总**：毛需求跨单相加、现存量取最大值（同一个物料库存不能相加）、净需求跨单相加 → 建议 = 请购 / 生产 / 委外加工 |
| 页面 | `/mes/mps`：左计划单、右物料需求；顶部按计划期生成 |

## 28. 销售流程图：改成「直接销售出库」闭环（2026-11-12）

### 28.1 旧图的问题

旧图把销售订单当中心，同时向右派生销货单、向下派生销售出库单和退货单，费用单从最下面
「选单」到分摊单——读起来是四条互不相干的支线：

- 出库单和销货单是平级分支，看不出「直接销售出库」是先扣库存再确认应收；
- 没有收款单，钱回不来，谈不上闭环；
- 没有库存节点，出库到底扣了什么完全看不见（用户重点提的库存联动）；
- 费用单只是挂了个「选单」箭头，分摊到哪儿（发票/客户/毛利）没有交代。

### 28.2 新结构（列模式，3 列 × 6 行，箭头一律向右/向下）

```
费用来源 (c0)      销售主链 (c1)            库存与退货 (c2)
                  报价单
                     ↓生单
                  销售订单
                     ↓生单
                  销售出库单 ────出库────→ 库存结存
                     ↓选单                     ↑退货入库
费用单            销货单                  销售退货单
 ↓生成分摊单         ↓生单
销售费用分摊单 ─→ 销售开票
  （分摊到票）       ↓收款核销
                  收款单
```

| 事实 | 依据 |
|---|---|
| 销货单可由销售出库单「选单」生成（直接销售不走产成品入库） | `SALE_INV` 选单 = 选销售订单 / 选销售出库单 |
| 应收挂在**销货单**，收款单按客户核销 | `FinanceSettleService.RECEIVABLE_PANELS = {SALE_INV}`；`RECEIPT` 核销按客户取未结 AR |
| 出库扣库存、退货回增，退货单审核还冲减应收 | `StockTxnService` 出库方向含 `SALE_OUT`、入库方向含 `SALE_RETURN`；`AR_RETURN` 来源 = 销售退货单 |
| 费用单 → 销售费用分摊单 → 分摊到发票 | `EXPENSE` 生单 = 生成销售费用分摊单；`SALE_COST_ALLOC` 选单 = 选费用单，明细带「分摊对象 / 销售发票号」 |
| 退货单没有生单入口，手工建单（来源单号填原单） | `SALE_RETURN` 无 selectConfig、无生单按钮 |

**费用分支为什么挪到左列**：原来「费用单 → 分摊单 → 发票」是两条从右往左的箭头，
既反着读、又触发了一个引擎 bug——同一行目标在左边时，连线仍然「右出左进」，
折线先往右伸再绕过整张卡片回到左侧，画面上留下一条伸出去的残线。现在费用单在左列、
分摊单在它下面，费用链变成「↓生成分摊单 → →分摊到票」，全程向右/向下。

**引擎修复**：连线锚点改由 `flow-layout.js` 的 `defaultHandles(a, b)` 统一判断——
跨行竖直（下出上进 / 上出下进），同一行按横坐标选边（目标在左 → 左出右进，用 `out-l` / `in-r`）。
这样任何模块里出现从右往左的边都不会再画出 U 形残线。

**不画的两条**：`FINISH_IN → 销货单`（生产发货路径，不属于直接销售）；
`SALE_OUT → SALE_RETURN`（没有这个生单入口，画出来是假流程）。

### 28.3 验收

- 结构由 `frontend/test/flow-layout.test.js` 钉住：10 节点 / 9 条边，主链五步缺一不可，
  库存两条（出库、退货入库）与费用两条（生成分摊单、分摊到票）必须存在，且必须有边指向 `RECEIPT`；
  另有 `defaultHandles` 用例盯「目标在左必须左出右进」；
- 折线几何脚本核对 9 条边：0 处穿卡、0 处标签压卡（标签中心见交接记录）；
- 页面刷新后主链是一条竖线，库存/退货/费用三条旁支各占一列。

## 29. 费用闭环：费用单 → 分摊单 → 发票分摊费用（2026-11-12）

### 29.1 原来断在哪

按图把这张链跑一遍（测试数据：运费 300 元），发现两处断点：

| 断点 | 现象 |
|---|---|
| 费用单审核不入账 | `AccountingService` 没有 `EXPENSE` 模板，`postAccounting` 拿到 null 模板直接返回 0，费用没有凭证 |
| 分摊单审批不落地 | 分摊单审核后既不回写发票、也不生成任何东西，「摊了等于没摊」，发票上永远看不到分摊费用 |

### 29.2 补的两段

1. **费用入账**：`AccountingService` 增加 `EXPENSE` 模板——借 `6601 销售费用` / 贷 `2202 应付账款`（费用发生即挂账，付款由付款单核销）。分摊单**不记账**（管理口径），避免同一笔费用记两次。
2. **分摊回写**：新增 `PanelActionHandler` 实现 `SaleCostAllocActionHandler`（动作「执行分摊」）：
   - 分摊单必须**已审核**；按明细的「销售发票号」汇总分摊金额（同一张票多行合并）；
   - 写回发票表头 `分摊费用`（累加）与 `分摊单号`；
   - 分摊单标记 `分摊状态 = 已分摊` + `执行时间`，**重复执行直接拒绝**（幂等，不会重复累加）；
   - 按客户分摊、没填发票号的行拒执行，并报出未分摊金额。
   `SaleCostLoopRegistry` 启动时给分摊单补 `分摊状态/执行时间 + 执行分摊按钮`、给销售发票补 `分摊费用/分摊单号` 字段。

### 29.3 实测（测试数据，2026-11-12）

```
费用单 FY-20261112-001（运费 300，含税 318，往来单位 华东铝业）
  提交审批 → 审批通过
  凭证：借 6601 销售费用 318 / 贷 2202 应付账款 318
```

## 30. 业务总览：审批标识 + 「卡在未审批」流光（2026-11-12）

### 30.1 做什么

业务总览的流程节点分不出「这个环节要不要审批」——图上看不出销售订单、采购入库这些面板是
走「提交审批 → 审批通过」的，而排产批次、工序汇报是生成即生效的。追踪一张单据时，也就看不出
卡点到底是「等下游」还是「等人审」。

现在每个节点带两种状态：

| 状态 | 表现 |
|---|---|
| 审批面板（走审批流） | 节点编号右侧一个灰色「审批」角标，悬停提示「该面板需要审批」 |

- **哪些面板要审批**：与后端 `PxService#APPROVAL_PANELS` 完全一致。前端没有接口能一次拿到全部

  漂移即失败（改后端忘了改前端会红）。

  已审核却卡住的说明是下游没跟上，不标成待审批（单测覆盖）。
  追踪接口本身已经给出卡点原因，例如 `PO-2026-08-0002 停在「草稿」，需要提交审核`。

## 31. 业务总览整页滚动修复（2026-11-12）

### 31.1 现象与根因

追踪一张 39 环节的单据后，业务总览**整页滚不动、下半截被裁**：模块流程图只露出一小条，
左侧模块导航也被切掉。

根因是页面根容器写死了高度：

```css
.bo-page { height: 100%; }   /* ← 问题在这里 */
```

它作为 `.portal-content`（`overflow: auto`）的子元素，高度恒等于视口：内容再多，
滚动容器的 `scrollHeight` 也等于 `clientHeight`，滚动条不出现；超出的部分被
`.portal-body { overflow: hidden }` 裁掉。第二个放大因素：`.bo-body { flex: 1; min-height: 0 }`
把图表区当成「可无限压缩」的弹性区，追踪路线一长，流程图就被压成一条。

### 31.2 修复

| 位置 | 改动 | 理由 |
|---|---|---|
| `.bo-page` | `height: 100%` → **`min-height: 100%`** | 内容超过视口时撑开页面，交给 `.portal-content` 滚动 |
| `.bo-body` | `flex: 1` → **`flex: 1 0 auto`** + `min-height: 520px` | 内容高时不被压扁，内容矮时仍填满剩余高度 |

同一处隐患一并修掉：`/wms/workbench`、`/mes/mps`、`/pdm/engChange` 三个新页面根容器也改成
`min-height: 100%`，窗口偏矮时同样是滚动而不是裁切。

### 31.3 回归哨

`frontend/test/approval-panels.test.js` 增加一条用例盯死这个写法：
`.bo-page` 必须含 `min-height: 100%`、不得再出现 `height: 100%`，`.bo-body` 必须是
`flex: 1 0 auto` 且带 `min-height`。断言前会先剥掉 CSS 注释——否则注释里「不能写 height:100%」
这句话会把新加的哨子误伤（这版就踩了一次，正则里 `\bheight` 还会匹配 `min-height` 的尾巴，
最终用 `(^|[\s;{])height:` 兜住）。

## 32. 首件报检单「一道工序一串单」的排查（2026-11-12）

### 32.1 现象

追踪 `SO-20261110-001` 时，工序汇报下面每道工序挂着 **5 张** 首件报检单
（车削：SJ-20261111-001/003/20261112-015/018/021，钻孔、抛光同样），看起来像「一工序多张首检」，
像是重复建单的数据污染。

### 32.2 结论：不是数据污染，是追踪归集串线

- **数据本身干净**：按「加工单 + 工序」分组查有效首检单，`cnt > 1` 的结果为空——
  每道工序只有一张有效首检单（另有 1 张作废的历史单 SJ-20261111-001）。
- **根因在 `ProcessTraceService#hitsOf`**：它用「解析不到加工单号就归到当前加工单」做兜底。
  这张销售订单同时有自制行和委外行，委外首检单引用的是委外加工单（`OUTSOURCE_ORDER`，
  不是 `MANU_ORDER`），解析不到就落进每条自制线的兜底 → **每道工序把别的加工单的首检单都挂上**。
  再加上作废的历史单也画在分支里，于是 5 张。
- **建单门限本来就有**：`createFirstInspectForProcess` 已有「同加工单同工序已有有效首检 → 不再建」的
  守卫，只有「已审核且判定不合格」才允许开重新首检单。

### 32.3 修的两处

1. `hitsOf` 不再兜底：新增 `ownMoOf(doc)` 严格解析单据自己的加工单；引用的是委外加工单时返回
   哨兵 `!<单号>` 直接排除；完全没有加工单引用的单据，只有在本次追踪里**只有一张加工单**时才归它。
2. 首检分支跳过 `作废` 单据（返工重检会作废旧单，画出来只会让人以为有多张在跑）。

### 32.4 门限与实测

- 门限（已有，本次补测试锁死）：同一加工单同一工序，有效首检单最多一张；
  `PxServiceFirstInspectPerProcessTest#sameProcessNeverGetsSecondInspection` 断言
  「车削首检已通过后再报车削，新建首检单数量 = 0」。
- 修复后重跑同一个追踪：

```
线 L1 SO-20261110-001-1  车削 → SJ-20261111-003 ｜ 钻孔 → SJ-20261111-004 ｜ 抛光 → SJ-20261111-005
线 L2 SO-20261110-001-2  下料 → SJ-20261111-002 ｜ 车削 → SJ-20261111-006 ｜ 铣削 → SJ-20261112-001
环节数 39、无卡点（与修复前一致，只是分支不再串单）
```

单测 `ProcessTraceServiceTest#firstInspectBranchesStayWithOwnManufacturingOrder`：
委外首检单不串进自制线、作废单不进分支、一道工序只剩自己那张。
