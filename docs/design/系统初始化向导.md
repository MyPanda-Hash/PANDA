# 系统初始化向导（AI 辅助开箱即用）

| 属性 | 内容 |
|---|---|
| 文档类型 | 设计方案 |
| 适用场景 | 新客户首次部署、空库初始化 |
| 维护状态 | 草案（待拍板，未实施） |
| 最后整理 | 2026-11-13 |
| 文档导航 | [文档中心](../README.md) · [后端逻辑设计](../backend/后端逻辑设计.md) · [前端面板设计](../frontend/前端面板设计.md) |

目标：**从空白库到「能下单生产」不超过 30 分钟，人只做上传与确认**。
输入是客户已有的组织架构图、员工名单、存货/BOM/工序/工艺路线表、库存期初；
输出是部门树、员工档案、账号与权限、主数据、期初库存。

## 0. 结论先说

| 判断 | 依据 |
|---|---|
| 技术路径可行，且**大部分地基建好了** | 面板通用运行时已有 INV/BOM/OP/ROUTE/INIT_BALANCE 的字段与保存链路；用户/角色/授权接口现成（`/api/sys/user/save`、`/api/sys/role/{id}/panels`）；期初余额审核即落 `stock_txn` |
| 真正的缺口不是「能不能写」，是**「AI 解析 → 可审阅的草案」这层契约** | 现有 `InitWizard.vue` 只有界面（476 行），完成时仅写 `localStorage.mes_init_done`，**一个字节都没落库** |
| 图片只能承担「组织架构 + 岗位职责」，主数据必须走表格 | 组织架构图没有行列坐标、岗位层级靠视觉猜测；存货/BOM/路线错一个字段就会连带下游单据错，必须可机读 |
| AI 不该直连数据库，也不该绕过权限 | 与既有边界一致（L2 只读 + 动作白名单）；落库始终在 MES 内、以当前管理员身份、留审计 |

## 1. 现状盘点（可复用的部分）

| 能力 | 现状 | 复用方式 |
|---|---|---|
| 初始化入口 | `frontend/src/layout/InitWizard.vue`：首次登录自动弹，用户下拉可再打开；三步「行业 → 特性 → 完成」，只写 localStorage | **复用这个壳**，把「完成」改成真实流程 |
| 部门/员工 | `sys_dept`（parent_id 树）、`EMP` 面板（员工编码/名称/所属部门/职务/手机…） | 直接落库 |
| 存货 | `INV` 面板（singleDoc）：存货编码/名称/规格/计量单位/计价方式/参考成本/工艺路线… | 直接落库 |
| 工序 | `OP` 面板（singleDoc）：工序编码/名称/默认车间/标准合格率%/计件依据… | 直接落库 |
| 工艺路线 | `ROUTE` 面板：表头 路线编码/名称/版本；明细 processes（工序顺序/工序编码/工资类型/计件依据/委外供应商…） | 直接落库 |
| BOM | `BOM` 面板：表头 产品编码/工艺路线编码；明细 children（父件/子件/定额数量/生产数量/损耗率%/预入仓库…） | 直接落库 |
| 期初库存 | `INIT_BALANCE` 面板：表头 仓库/单据日期；明细 存货编码/数量/主单价/金额 → 审核后落 `stock_txn(IN)` → `stock_balance` | 直接落库 + 审核 |
| 账号 | `/api/sys/user/save`（新增/改，密码 BCrypt）、`sys_user.role_id/dept_id` | 直接调用服务层 |
| 权限 | `sys_role_panel`：`perms` 逗号串，12 个动作（view/query/add/generate/edit/delete/export/print/audit/price/review/adjust）；admin 全权 | 直接调用 `RoleService.saveRolePanels` |
| 表格导入 | `ImportDialog.vue` 在前端解析 Excel（列名→字段名），逐行保存 | 向导里可复用解析逻辑，但落库改走后端批量 |
| AI | 数字员工 `doc-nexus-ai`：已有 `MesClient`（只读）+ 工具路由；模型走 WorkBuddy 中转 | 新增「解析资料 → InitDraft」能力 |
| OCR（阿里云） | 配置项在（`mes.ocr.*`），但 `.env.local` **未配 AK** | 若走 MES 内置 OCR 需先配凭证；走数字员工的 VLM 则不需要 |

## 2. 总体设计

```text
客户资料                     解析层（AI，可替换）              落库层（MES，唯一写入口）
组织架构图(png)  ┐                                          ┌→ 部门树 sys_dept
员工名单(xlsx/文本)├→ 数字员工：抽取 + 归一 →  InitDraft → 人工确认 → InitWizardService
存货/工序/路线(xlsx)│   （结构化 JSON，带 evidence）      ↑            └→ 主数据 / 账号 / 权限 / 期初
BOM/期初(xlsx)   ┘                                    预览编辑器（逐条可改）
```

三条硬约束：

1. **AI 只产出草案**，不写库、不调 `/api/px/*` 的写接口。草案是一份带 schema 的 JSON，可存档、可重放、可 diff。
2. **落库只有一条路**：`InitWizardService`（MES 内），逐阶段校验 + 事务 + 审计（`sys_usage_log`，`event_type=INIT`）。
3. **人一定在环**：每类数据一屏预览，红黄绿标注（绿=可直接落、黄=需确认、红=缺必填/冲突），确认后才执行。

## 4. 权限映射（岗位 → 角色 → 面板矩阵）

内置一套可改的模板（放 `panel_config` 的 `INIT_ROLE_TEMPLATES`，或独立配置表）：

| 岗位模板 | 面板范围 | 关键动作 |
|---|---|---|
| 总经理/厂长 | 全部业务面板（只读） + 报表 | view/query/export/audit |
| 销售员 | 报价单/销售订单/销货单/销售出库单/销售发票/客户 | view/query/add/edit/print（无 delete、无 price） |
| 销售主管 | 同上 + 审批 | 追加 audit、price |
| 计划员 | 销售订单/主生产计划/加工单/排产/采购需求分析 | view/query/add/edit/generate |
| 采购员 | 请购/采购订单/到货/采购入库/采购发票/供应商 | view/query/add/edit/generate/print |
| 仓管员 | 库存/出入库/调拨/盘点/配货/仓内作业 | view/query/add/edit/adjust（无 price） |
| 质检员 | 到货检验/委外检验/首件/成品报检/检验单/检验项目 | view/query/add/edit/audit |
| 车间工人 | 生产领料/工序报工/首件报检（只增） | view/query/add |
| 财务 | 收付款/核销/发票/费用/凭证/往来对账 | view/query/add/edit/export |

匹配规则（AI 只猜，**人可改**）：

- 职责含「审批/审核/签核」→ 加 `audit`；含「定价/报价/调价」→ 加 `price`；含「盘点/调账」→ 加 `adjust`；含「导出报表」→ 加 `export`。
- 只读岗位（如「统计员」）不给 `add/edit/delete`。
- `delete` 默认只给主管；`price` 默认只给主管与财务，**这条要在预览页显著提示**。

账号策略：

- `user_name` 优先工号；缺失用「姓名拼音全拼」，重名加序号（`zhangwei2`）。
- 初始密码：一人一随机 12 位，向导结束页可导出 CSV（账号/初始密码/所属角色），**密码不在界面明文回显，只允许一次下载**。
- 新增 `sys_user.must_change_password`（Flyway `V4`），首次登录强制改密；`admin` 不动。

## 5. 落库顺序与依赖

```text
① 部门 sys_dept          （无依赖）
② 员工 EMP              （依赖 部门）
③ 存货 INV              （依赖 计量单位 UOM、工艺路线编码可空）
④ 工序 OP               （无依赖）
⑤ 工艺路线 ROUTE        （依赖 工序）
⑥ BOM                   （依赖 存货 + 工艺路线）
⑦ 期初库存 INIT_BALANCE （依赖 存货 + 仓库；审核后落 stock_txn）
⑧ 角色 + 面板权限        （依赖面板已存在）
⑨ 账号 sys_user         （依赖 部门 + 角色）
```

每阶段独立事务 + 独立进度：①失败不阻塞 ④，但 ⑥ 必须等 ③⑤ 成功。页面上按阶段显示「已完成/跳过/失败原因」。

## 6. 幂等、校验、回滚

| 机制 | 做法 |
|---|---|
| **dry-run** | `POST /api/init/wizard/validate` 只校验不落库，返回 `{errors, warnings, plan}`；页面「先试算」 |
| **自然键去重** | 存货编码 / 工序编码 / 路线编码 / 员工编码 / 用户名 / (父件,子件,版本) 已存在则跳过并记为 `skipped` |
| **批标记** | 新建 `init_batch`（id、operator、source 摘要、create_time）+ `init_batch_item`（batch_id、target、自然键、行 id、action）；每个写入登记一条 |
| **撤销** | 「撤销本次初始化」按 `init_batch_item` 逆序删除**本次创建且未被后续业务引用**的记录；被业务引用的（已下过单的存货）只提示不删 |
| **一致性自检** | 结束页输出：部门数/员工数/存货数/路线数/BOM 行数/期初合计金额/可登录账号数 + 8 条抽查（BOM 引用的子件都存在、路线引用的工序都存在、期初余额 = 明细合计） |
| **重复执行** | 同一份草案可重放；全部命中「已存在」时结果为零变更，页面提示「无新增」 |

## 7. 接口草案

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/init/wizard/parse` | 上传文件 → 返回 InitDraft 片段（**代理到数字员工**；MES 不直接调模型） |
| POST | `/api/init/wizard/validate` | dry-run：校验草案，返回问题清单与计划 |
| POST | `/api/init/wizard/apply` | 按阶段落库，返回 batchId + 每阶段结果 |
| GET | `/api/init/wizard/batches/{id}` | 本次初始化明细（撤销前预览） |
| POST | `/api/init/wizard/rollback` | 撤销某 batchId 创建的记录 |

权限：只允许 `admin`（`RoleService.isAdminUser`）；草案与结果全部写 `sys_usage_log`。

## 8. 分阶段实施

| 阶段 | 内容 | 产出 | 估时 |
|---|---|---|---|
| **P0 骨架** | InitDraft schema + `InitWizardService`（②③④⑤⑥⑦ 主数据 + dry-run + 幂等 + batch 表）+ 向导壳改造（表格上传，无 AI） | 无 AI 也能用：上传 Excel 完成主数据初始化 | 2 天 |
| **P1 组织与账号** | ①②⑧⑨：部门树、员工、角色模板、账号生成、首登改密（V4 迁移） | 上传名单即可批量建号并配好权限 | 1.5 天 |
| **P2 AI 解析** | 数字员工新增 `parse_org_chart` / `parse_roster` / `parse_item_sheet`，输出 InitDraft 片段 + evidence；MES 侧预览编辑器 | 架构图 + 名单直接出草案 | 2 天 |
| **P3 收尾** | 撤销/重跑、自检报告、初始化文档与演练脚本（空库一次性跑通） | 可交付给实施人员 | 1 天 |

合计约 **6.5 个工作日**；P0+P1 做完就已经是「可交付的初始化工具」，P2 才是「AI 辅助」。

## 9. 验收标准（开箱即用）

空白库跑一遍向导后，新账号登录必须能做到：

1. 看到该岗位应看到的菜单（不该看到的一个都不出现）；
2. 新建销售订单 → 审核 → 生成生产加工单，**BOM 与工艺路线自动带出**（含工序、定额、损耗）；
3. 库存状况表能查到期初余额，且 `库存台账` 有对应的期初事务；
4. 用仓管账号能领料出库、用质检账号能报检、用财务账号能看到应收；
5. 抽查 10 条数据与客户原表逐字段一致；
6. 撤销初始化后，本次创建的主数据全部消失、无残留孤立记录。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 组织架构图识别错（层级、跨部门虚线汇报） | 部门树错、权限挂错部门 | 图只用于建部门树 + 岗位；**员工与部门归属在预览页逐条确认**；虚线汇报忽略（系统只有一级 dept_id） |
| 客户表格列名与系统字段不一致 | 导入大批失败 | 预览页做「列映射」步骤（复用 `ImportDialog` 的列名匹配思路），映射结果可存为模板下次复用 |
| BOM/路线数据量大（几百行） | 单事务超时 | 分批提交（每 200 行一批）+ 断点续传（按 batch 记录进度） |
| 权限给多了（尤其 delete/price） | 数据被误删、价格外泄 | 危险动作默认关闭；预览页把「delete/price/adjust」单独高亮；落库后输出权限矩阵供管理员复核 |
| 期初库存直接审核 | 库存与财务口径立刻生效，错了要冲销 | 默认只生成**草稿**期初单，由财务在预览页勾选「同时审核」才落库存 |
| AI 解析结果不可解释 | 客户不敢用 | 每条草案带 `evidence`（来源文件 + 页/行/图区域），可点回原图核对 |

## 11. 需要拍板的四件事

1. **AI 放哪**：数字员工做解析（推荐，MES 保持"只接收结构化草案"），还是 MES 内直接调模型（耦合度高、凭证管理分散）？
2. **图片解析边界**：接受「组织架构图只用于部门树与岗位，员工/职责必须配名单」这个前提吗？若要求纯图片出全部员工，误差与返工成本会显著上升。
3. **初始密码策略**：一人一随机串（更安全、需分发）还是「工号 + 手机后四位」（好记、需强制首登改密）？
4. **期初库存默认落草稿还是直接审核**？（建议草稿 + 勾选审核）
