## 0. 已锁定的决策（2026-11-13 用户拍板）

| 编号 | 决策 | 影响 |
|---|---|---|
| D1 | **AI 解析放数字员工**，MES 只接收结构化草案 | MES 不内置模型调用，不持有模型凭证 |
| D2 | 初始化**允许写 MES 内部数据**（部门/员工/存货/工序/路线/BOM/期初/角色/账号） | 需要受控写通道，见 §7 |

## 2. 总体流程

```text
① 下载模板（7 份 xlsx，系统生成）
② 客户填表
③ 分模块上传 → 解析（Excel 直接解析；组织架构图交数字员工抽部门/岗位）
④ 预览（表格可改，红黄绿标注）→ 校验（自然键、必填、引用完整性）
⑤ 确认落库（按模块独立事务）→ 结果页（新增/跳过/失败逐条）
⑥ 期初库存：弹窗列表核对 → 手工改 → 确认 → 落 INIT_BALANCE 并审核 + 写证据表
⑦ 全部模块完成后 → 账套锁定（不可再次初始化）
```

```jsonc
{
  "version": "1.0",
  "module": "items",                       // depts|employees|items|processes|routings|bom|openingStock
  "sourceFile": "存货.xlsx",
  "rows": [
    { "存货编码": "CP001", "存货名称": "铝棒 Φ80", "规格型号": "Φ80×3000",
      "计量单位": "件", "计价方式": "全月平均", "参考成本": 20, "工艺路线": "GY-CP001" }

  "warnings": ["第 3 行「计量单位」为空，已按「件」补齐"],
  "evidence": [{ "row": 2, "cell": "B2", "confidence": 0.98 }]   // 图片解析才带

```

## 5. 落库顺序与依赖

```text
① 组织架构 sys_dept          （无依赖）
② 员工 EMP                    （依赖 部门）
③ 存货 INV                    （依赖 计量单位；工艺路线可后补）
④ 工序 OP                     （无依赖）
⑤ 工艺路线 ROUTE              （依赖 工序）
⑥ BOM                         （依赖 存货 + 工艺路线）
⑦ 期初库存 INIT_BALANCE       （依赖 存货 + 仓库；证据表 → 落单 → 审核）
⑧ 角色 + 面板权限             （依赖面板已存在）
⑨ 账号 sys_user               （依赖 部门 + 角色；密码统一 123456）
```

前端按此顺序排列模块卡片，已完成打勾；未满足前置的模块置灰并提示「先完成 X」。

## 6. 期初库存：核对 + 证据表（D6 / D7）

**流程**（这是用户明确要求的顺序）：

1. 上传 `opening-stock.xlsx` → 解析成行（只进暂存，**不落库**）
2. **弹窗列表展示**：仓库 / 存货 / 规格 / 单位 / 数量 / 主单价 / 金额（数量×单价自动算）
3. 允许**逐行手工修改**数量、单价、仓库；改过的行标黄并显示「原值 → 现值」
4. 界面上给合计：行数、数量合计、金额合计
5. 点「确认并写入期初」→ 一个事务内：写证据表 → 生成 `INIT_BALANCE` 单据 → 审核（落 `stock_txn`）→ 汇总 `stock_balance`
6. 完成后页面上可查「期初凭证」，导出留档

**证据表 `init_balance_evidence`**（新表，防止事后扯皮）：

| 列 | 说明 |
|---|---|
| `id` / `batch_id` | 批次 |
| `source_file` / `source_row` | 原始文件名与行号（能回到那张 Excel 的第几行） |
| `item_code` / `item_name` / `spec` / `unit` | 存货四要素（原始与确认值各一份见下） |
| `warehouse_input` / `warehouse_confirmed` | 仓库：原始 / 确认 |
| `qty_input` / `qty_confirmed` | 数量：**原始值 / 确认值** |
| `price_input` / `price_confirmed` | 单价：原始 / 确认 |
| `amount_confirmed` | 金额 = 确认数量 × 确认单价 |
| `changed` | 是否被手工改过（由 `_input` 与 `_confirmed` 比较得出） |
| `init_balance_no` | 落库后关联的期初单号（可反查单据） |
| `operator` / `confirmed_at` | 谁在什么时候确认的 |

另存整个上传文件原文件（`init_upload` 表存字节或落磁盘 `backup/init-attachments/`），保证「报表 ↔ 证据 ↔ 原始文件」三重可追溯。

**规则**：
- 证据表只增不改；`_input` 系列一经写入不再更新，修改只写 `_confirmed`。
- 单据与证据同一事务，任一失败全回滚（不会出现「有证据没库存」）。
- 撤销只在**锁之前**允许：删单据 + 删事务 + 证据表标记 `voided`（不物理删）。

## 7. 一次性锁与管理员保护（D3 / D8）

### 7.1 账套锁

新表 `init_state`（单行）：

| 列 | 说明 |
|---|---|
| `batch_id` | 当前/最后一次初始化批次 |
| `modules_done` | 已完成模块（逗号串） |
| `locked` | **true = 已初始化完成，禁止再导入** |
| `locked_at` / `locked_by` | 锁定时间与人 |

- 每次 `apply` 先查 `locked`，为 true 直接 409「本账套已完成初始化，不允许再次导入」。
- 全部 7 个模块都完成（或有明确「跳过」）后，点「完成初始化」→ `locked = true`。
- **没有界面入口可解锁**；确需重来只能由实施人员直连数据库处理，并在 `sys_usage_log` 留说明。这条写进交付文档。
- 锁只对「初始化导入」生效，不影响之后的正常业务录入与主数据维护。

### 7.2 管理员保护（硬约束）

在 `InitService` 的所有写入路径上：

1. `sys_user.user_name = 'admin'` 的记录**永不插入、永不更新**（包括密码、角色、部门、启用状态）。
2. `sys_role.is_admin = 1` 的角色：不接受模板改写；`saveRolePanels` 对管理员角色本就抛错（现有逻辑），初始化侧再兜一层。
3. 草案里若出现「把 admin 的 role 改成普通角色」「给 admin 加禁用」「删除 admin 角色」等意图 → **整批拒绝**并返回明确原因，不做部分成功。
4. 初始化创建的账号一律**非管理员**；模板里若有人填了「管理员」岗位，落库时降级为对应业务角色并给出警告。
5. 单测固化：这三条必须有失败用例（见 §10）。

## 8. 分批上传的状态机

每个模块独立状态：`未开始 → 已上传(待校验) → 校验失败 / 待确认 → 已落库 → 已跳过`。

- 校验失败不阻塞其它模块，但**前置未完成时后续模块置灰**（§5 顺序）。
- 「已跳过」用于客户没有某类数据（例如不做 BOM），需在完成页显式列出，避免事后说"忘了导"。
- 每模块可重复上传替换**尚未落库**的草案；已落库的只能在该模块内做增量（自然键去重，新增行照常导入）。

## 9. 接口草案

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/init/state` | 当前批次、已完成模块、是否已锁定 |
| GET | `/api/init/template/{module}` | 下载该模块 xlsx 模板 |
| POST | `/api/init/parse` | 上传文件 → 解析成草案行（Excel 本地解析；图片转数字员工） |
| POST | `/api/init/validate` | dry-run 校验，返回 errors/warnings/计划 |
| POST | `/api/init/apply` | 按模块落库（部门/员工/存货/工序/路线/BOM/角色/账号） |
| POST | `/api/init/opening/confirm` | 期初库存：提交核对后的行 → 证据表 + 期初单 + 审核 |
| GET | `/api/init/opening/evidence?batchId=` | 查期初证据（含原始/确认值） |
| POST | `/api/init/finish` | 置 `locked=true`，返回完成报告 |

权限：`admin` 专用；每次写操作记 `sys_usage_log(event_type=INIT)`。

## 11. 验收标准（空白库跑一遍必须满足）

1. 7 份模板都能从系统下载，表头与本文档一致；
2. 上传后能逐条看到「新增 / 跳过（已存在）/ 失败（原因）」；
3. 期初库存弹窗能改数量与单价，改后合计即时更新；
4. 确认后：`INIT_BALANCE` 已审核、`stock_txn` 有 IN 事务、`stock_balance` 与 Excel 一致、证据表有原始值与确认值；
5. 用新账号（密码 123456）登录，菜单与权限符合其岗位；
6. `admin` 的密码、角色、权限在初始化前后**完全一致**（逐字段比对）；
7. 完成后再次调用 `/api/init/apply` 返回 409，界面无「重新初始化」入口；
8. 抽查 10 条主数据与客户原表逐字段一致。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 组织架构图识别错（层级/虚线汇报） | 图片只出部门树与岗位草案，**必须人工确认**；虚线汇报忽略（系统只有一级 `dept_id`） |
| 客户 Excel 列名/顺序不对 | 模板固定表头 + 解析时按表头匹配；匹配不上给出「缺哪列」而不是整批失败 |
| BOM/路线几千行 | 分批提交（每 200 行）+ 断点续传（`init_batch_item` 记进度） |
| 期初数量填错却已锁账 | 证据表留原始值与操作人；锁之前允许撤销重来；锁之后走正常业务调整（盘点/调整单），不再走初始化 |
| 客户想「再导一次」 | 锁 + 明确的替代路径：主数据走面板导入，期初走盘点/调整单 |
| 管理员被弱化 | §7.2 五条 + 单测固化 |
