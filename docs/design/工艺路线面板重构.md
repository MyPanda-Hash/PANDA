## 1. 问题（已核实的现状）

ROUTE 面板当前是 `singleDoc: true`（单单据档案），整个面板**只有 1 条 form_data 记录**（`编号=工艺路线`，状态「已审核」），三条工艺路线 GY-001 / GY-002 / GY-003 的全部工序混在这张单据的 `detail.processes` 里，共 10 行（运行库实时读取；`init.sql` 种子基线为 13 行）。

因此：

| 症状 | 根因 |
|---|---|
| 「工艺路线编码」「工艺路线名称」每行重复填写 | 它们是**明细字段**，不是表头字段 |
| 列表一屏看到全部工序混排，分不清哪几行属于同一条路线 | 明细行靠 `工艺路线编码` 值人为分组 |
| 工序没有可靠先后 | 顺序仅由 `加工顺序` 一个整数字段承载，且这列可以随便改、可以重复 |
| 一条路线无法作为整体被选单/引用 | 单据身份是 `编号=工艺路线` 这一个常量，与路线无关 |

排产（`resolveProcesses`）与手工建单（`applyRouteProcesses`）都靠 `routeRowsOf(routeCode)` 遍历**全部** ROUTE 单据、再按 `工艺路线编码` 过滤行。这条链路能跑，但依赖「行里存着编码」这一脆弱约定。

## 2. 目标结构

**一个工艺路线 = 一张单据**（主从结构）。

```
form_data (ROUTE)
├─ 编号        = ROUTE-001         ← 单据身份（后端生成，不面向用户）
├─ data.工艺路线编码 = GY-001      ← 表头，用户自填
├─ data.工艺路线名称 = 铝棒Φ80加工路线  ← 表头，用户自填
├─ data.停用        = false        ← 表头
└─ detail.processes[]
   ├─ 行1: 工序编码=PX001 下料   加工顺序=1
   ├─ 行2: 工序编码=PX002 车削   加工顺序=2
   └─ 行3: 工序编码=PX007 检验   加工顺序=3
```

### 2.1 字段归属调整

| 字段 | 现在 | 改为 | 依据 |
|---|---|---|---|
| 工艺路线编码 | 明细字段（每行重复） | **表头**，`isRequired`，用户可自填 | 单据身份，BOM 参照它 |
| 工艺路线名称 | 明细字段（每行重复） | **表头** | 同上 |
| 停用 | 明细字段 | **表头** | 停用是整条路线的属性，不是单道工序的 |
| 加工顺序 | 明细字段，界面可见可改 | 明细保留，**界面隐藏**，按行序自动编号 | 排产、工序汇报、完工推进共 8 处依赖它排序 |
| 工序顺序 | 无（原先靠行号猜） | **新增只读列**，读路径按加工顺序算出 1..N | 明细区块没有行号列，不看这列看不出「哪道先做」 |
| 工序编码/名称/车间/工价/… | 明细字段 | 不变 | 这些确实是每道工序自己的属性 |

「加工顺序」不删数据，只从界面列里去掉；后端按行位置自动写入 1、2、3…，保证排产顺序唯一且无重复。

读出口再兜一层：`normalizeRouteDetailForRead` 在列表与表单两条路径上按「加工顺序」排序，并给每行写
`工序顺序 = 1..N`（`computed + readonly`）。原因是历史数据、迁移数据或手工改库都可能让数组顺序与加工顺序
不一致（实测乱序存储时接口原样返回，界面就跟着乱）；排产与工序汇报都依赖这个先后，不能靠存储顺序。

### 2.2 移除 `singleDoc`

`metadata.singleDoc` 置为 `false`（或删除该键）。这样：

- 列表恢复「一行一条路线」，顶栏「第 x/y 张」翻的是路线，不再是唯一的「工艺路线」单据；
- BOM 参照 ROUTE 时，前端不再走 `flatMap(detail[tabKey])` 展平分支（[engine.js:170-179](../../frontend/src/business/engine.js)），而是直接读单据行；
- 因此 `refField: 工艺路线编码` 必须能在**单据行顶层**取到值——由 2.1 的表头化保证。

这是本次改造最关键的跨端契约：**BOM 的 `工艺路线编码` 参照能否取到值，取决于 ROUTE 表头是否有这个字段**。

## 3. 交互设计

### 3.1 列表

一行一条工艺路线：`工艺路线编码 | 工艺路线名称 | 停用 | 工序数 | 工序摘要 | 单据状态`。

- 点行 → 下方明细区显示该路线的工序序列（按加工顺序升序，界面显示「第 N 道」而非裸数字）
- 「新增流程」→ 直接新建一张路线单据，表头填编码与名称
- 明细区保留现有能力：列头筛选、复制到剪贴板、另存为 EXCEL 模板

### 3.2 工序录入：一行选多工序

现状 `RefPickDialog` 已支持 `mode='detail'` 多选，`onDetailRefConfirm`（[PanelxList.vue:1892-1927](../../frontend/src/core/views/PanelxList.vue)）会「勾选 N 行 → 当前行填第一行，其余各生成一条明细」。本设计**复用这条既有链路**，不新造组件：

1. 明细区新增行 → 工序编码单元格点击 → 打开工序参照（OP 面板，`filter: {是否停用: false}`，共 5 道：下料/车削/铣削/热处理/检验）
2. 勾选多道工序 → 确定 → 每道生成一行，`refMap` 自动带出车间/加工方式/工资类型/计件依据/合格率
3. 后端保存时按行序写入 `加工顺序 = 1..N`

这满足「一行选择多工序」，且天然保证顺序 = 勾选顺序。

### 3.3 编码与名称自填

表头 `工艺路线编码` / `工艺路线名称` 设为普通文本字段（`isRequired: true`），不再自动生成。`metadata.autoCodeField` 从 `工艺路线编码` 改为 `单据编号`，让后端不再按路线编码规则生成编号——单据 `编号` 由 `DocNoRules` 按日期序号生成（`ROUTE-20261108-001` 形态），与用户填的 `工艺路线编码` 解耦。

> 注意：`isArchivePanel()` 对 ROUTE 的判定依赖 `autoCodeField`。改动后 ROUTE 仍在 `APPROVAL_PANELS` 里，该方法第一个分支就返回 false，行为不变（保存为草稿、走审核链路）。已核对 [PxService.java:7233-7240](../../backend/src/main/java/com/mes/service/PxService.java)。

## 4. 后端改动

### 4.1 `routeRowsOf(routeCode)` 兼容两种存储

改造后新数据：`data.工艺路线编码 == routeCode` 的单据，取其全部 `processes` 行。
历史数据：`singleDoc` 单据里按行内 `工艺路线编码` 过滤。

两种都要支持，且**迁移完成后旧分支仍保留**（防止有环境未迁移）：

```java
List<Map<String, Object>> routeRowsOf(String routeCode) {
    // 1) 新结构：表头带 工艺路线编码 的单据
    // 2) 旧结构：行内带 工艺路线编码（singleDoc 单张单据）
    // 合并去重后按 加工顺序 排序
}
```

排序改为「`加工顺序` 优先，缺失时按行数组下标」，不再依赖 `Double.compare` 对 null 的行为。

### 4.2 保存时按行序编号

在 ROUTE 保存路径（`callButton` → 保存）里，对 `detail.processes` 写入 `加工顺序 = index + 1`，并清掉行内的 `工艺路线编码` / `工艺路线名称` / `停用` 冗余副本（以表头为准）。这样旧字段不残留在行里，避免两处数据不一致。

> 若保留行内副本，一旦表头改名，行内旧值会让 `routeRowsOf` 的旧分支误命中。**必须清理**。

### 4.3 `fillInvRoute` / `resolveProcesses` / `applyRouteProcesses`

三者都调用 `routeRowsOf`，改完 4.1 后自动受益。`resolveProcesses` 里有一处独立排序（[PxService.java:4224](../../backend/src/main/java/com/mes/service/PxService.java)），要和 4.1 的排序口径统一，抽成同一个比较器。

## 5. 数据迁移

现有 1 条 `编号=工艺路线` 的单据，含 GY-001（3 行）、GY-002（4 行）、GY-003（3 行）。

迁移脚本（一次性，节点侧走 API 或直连数据库）：

1. **备份**：`SELECT * FROM form_data WHERE panel_code='ROUTE'` 导出 JSON 到 `docs/ref/mes-live/route-migration-backup-<date>.json`
2. 按 `工艺路线编码` 分组
3. 每组生成一条新 `form_data`：
   - `form_no` = `ROUTE-001/002/003`（沿用原 `编号` 字段里的 `ROUTE-001-1` 前缀序号，保证可追溯）
   - `data` = `{工艺路线编码, 工艺路线名称, 停用, 备注}`
   - `detail.processes` = 该组行，去掉 `工艺路线编码`/`工艺路线名称`/`停用`，重排 `加工顺序` 1..N
   - `status` = 原状态「已审核」
4. 原单据置为「已关闭」（**不删除**，保留回滚路径）
5. 校验：`routeRowsOf('GY-001')` 返回 3 行、顺序为 PX001→PX002→PX007

## 7. 风险与回滚

| 风险 | 处置 |
|---|---|
| 迁移后 BOM 参照取不到值 | 迁移后立刻验证 BOM 表单下拉；取不到则回滚（原单据仍在，状态改回「已审核」） |
| 旧行内冗余字段导致重复命中 | 迁移时清理，后端 `routeRowsOf` 去重 |
| `autoCodeField` 改动影响编号 | 已核对 `isArchivePanel` 首分支对 ROUTE 提前返回，无影响；用单测覆盖 |
| 排产顺序错乱 | 排序口径抽成单一比较器，单测覆盖「加工顺序缺失」场景 |

## 8. 排产顺序来自工艺路线的验证链

「工序先后是排产依据」这句话要能落地，必须整条链都成立。逐段取证（2026-11-09 实测）：

| 环节 | 位置 | 证据 |
|---|---|---|
| ① 路线内顺序 | `routeRowsOf` | 按 `加工顺序` 排序；缺失时按行序兜底（`PROCESS_SEQ_ORDER`） |
| ② 产品绑路线 | BOM 表头 `工艺路线编码` | `BOMF-002`：产品 `CP004` → `GY-002` |
| ③ 加工单展开 | `resolveProcesses` / `applyRouteProcesses` | 按 ① 的顺序逐道写入，`加工顺序 = 1..N` 重新编号 |
| ④ 排产看板 | `planBoard` | 按 `加工顺序` 排序输出 `工序顺序 = 1..N` |
| ⑤ 额度依赖 | `planBoard` 可排产量 | 第 1 道 = 加工单数量；第 k 道 = **上道合格量** − 本道已排产 |

实测数据（同一时刻）：

```text
GY-002 路线：1.下料 → 2.铣削 → 3.热处理 → 4.检验
MO-20261106-011（CP004）：1.PX001 → 2.PX003 → 3.PX005 → 4.PX007   ← 与路线一致
planBoard(MO-20261106-011)：顺序 1/2/3/4 与路线一致
planBoard(MO-20261106-007)：下料合格 2 → 铣削上道合格量 2 → 检验上道合格量 2（额度沿链传递）
planBoard(MO-20261106-011)：下料尚未报工 → 后续工序可排产量均为 0（不报工就不许排下道）
```

回归保护：`PxServicePlanBoardTest#planBoardFollowsRouteSequence`。
它把路线**乱序存储**（加工顺序 3,1,2），断言加工单工序与排产看板都必须是 `1,2,3`——
去掉排序实现该测试立刻变红。
