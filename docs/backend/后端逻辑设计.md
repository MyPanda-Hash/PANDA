# 轻 MES 后端逻辑设计

| 属性 | 内容 |
|---|---|
| 文档类型 | 后端设计 |
| 适用场景 | 后端逻辑设计 |
| 维护状态 | 生效 |
| 最后整理 | 2026-08-27 |
| 文档导航 | [文档中心](../README.md) |

本文描述当前 Spring Boot + MySQL 后端。系统只保留 SQL 链路，不依赖外部 PanelX 服务，也不提供 Mock 运行模式。

## 1. 总体结构

```text
浏览器 /api/*
  -> SecurityConfig + JwtAuthFilter
  -> Controller
  -> PanelRuntimeService
  -> PxService + PanelActionHandler
  -> MyBatis-Plus Mapper
  -> MySQL light_mes
```

| 层 | 主要实现 | 职责 |
|---|---|---|
| 配置与安全 | `config/` | JWT、Spring Security、CORS、分页和异常归一化 |
| 通用面板契约 | `panel/` | 运行时接口、动作上下文和业务 Handler 注册 |
| 接口 | `controller/` | 参数接收和统一 `ApiResult` 返回 |
| 业务 | `service/` | 面板 CRUD、审批、权限、生单、报表和 Dashboard 聚合 |
| 数据访问 | `mapper/`、`entity/` | MyBatis-Plus 实体与查询 |
| 初始化 | `resources/db/init.sql` | 建库、建表和新环境种子数据 |

## 2. 数据权威源

| 表 | 用途 |
|---|---|
| `panel_config` | 面板字段、列表、按钮、状态和选单配置 JSON |
| `form_data` | 通用单据表头 `data`、明细 `detail_data` 和单据状态 |
| `form_approval` | 提交、通过、驳回和弃审记录 |
| `sys_user`、`sys_role`、`sys_role_panel` | 用户、角色、可见面板和审批权限 |
| `sys_dept` | 组织树与用户归属 |
| `sys_menu`、`factory` | 门户菜单和工厂信息 |
| `manu_order`、`manu_order_item` | 传统生产加工单接口使用的结构化业务表 |

运行库是当前配置和数据的权威源；`init.sql` 是新环境初始化基线。修改运行库后，应把可重复的结构和配置同步回初始化 SQL，避免新部署与现有环境漂移。

`form_data` 的业务唯一键是 `(panel_code, form_no)`。表头和明细 JSON 必须保持以下边界：

```json
{
  "panelCode": "MANU_ORDER",
  "编号": "MO-...",
  "单据状态": "草稿",
  "detail": {
    "products": [],
    "materials": [],
    "processes": []
  }
}
```

## 3. 接口分组

| 路径 | 主要职责 |
|---|---|
| `/api/auth/*` | 登录、当前用户和权限 |
| `/api/px/*` | 通用面板配置、查询、表单描述、按钮动作和删除 |
| `/api/dashboard/stats` | Dashboard 聚合数据 |
| `/api/sys/menu/*` | 菜单树 |
| `/api/sys/user/*`、`/api/sys/role/*`、`/api/sys/dept/*` | 组织和权限管理 |
| `/api/manu/order/*` | 结构化生产加工单接口 |
| `/api/portal/*`、`/api/base/factory/*` | 门户角标、公告和工厂信息 |

`PxController` 只依赖 `PanelRuntimeService` 并做协议转换。当前 SQL 实现是 `PxService`：

- `getPanelConfig`：读取并升级运行时配置。
- `getPermMatrix`、`getNewFormPermMatrix`、`getFormDescriptor`：生成页面权限和表单描述。
- `queryFormDataList`：按面板分类查询普通单据、单单据档案或报表。
- `callButton`：在事务中处理保存、状态变化、审批和推式生单。
- `deleteForms`：按面板编码和单号删除。

通用生命周期未识别的按钮交给 `PanelActionRegistry`。一个动作只能匹配一个 `PanelActionHandler`；没有处理器或多个处理器同时匹配都立即失败。Handler 在 `callButton` 的事务中运行，可拥有自己的 Mapper 和领域 Service，禁止反向调用 Controller。

## 4. 创建和保存

1. 新建请求进入 `PxService.create/save`。
2. 后端按面板生成不重复的 `form_no`，并补齐单据日期、自动编号和配置默认值。
3. 新单状态默认为草稿；档案类面板按其启用规则保存。
4. 更新时以 `编号` 定位原记录。请求未携带明细时保留原 `detail_data`，禁止写成空值。
5. 保存前完成必填、编号、来源单和业务约束校验。

编号生成不得使用记录总数推算。新增前缀在 `PxService.generateFormNo` 登记，并依赖数据库唯一键处理并发冲突。

## 5. 状态与审批

```text
普通审核：草稿 --审核--> 已审核 --弃审--> 草稿
审批流程：草稿 --提交审批--> 审批中 --审批通过--> 已审核
                                  +--审批驳回--> 草稿
已审核/生产中 --手工完工--> 已完工
可执行状态 --中止--> 已中止 --取消中止--> 草稿
```

- 所有状态变化由后端再次校验，前端置灰不能代替服务端规则。
- 普通审核和审批流程互斥。启用审批的面板禁止“审核”直达已审核；兼容旧客户端时，旧“审核”动作按“提交审批”处理。
- 审批面板统一归一为一个“审批”组，动作顺序固定为提交审批、审批通过、审批驳回、审批情况和弃审。
- 提交、通过、驳回和弃审在同一事务内更新状态并写入 `form_approval`，操作人从当前 JWT 身份取得。
- 审批通过或驳回前，最近一条审批记录必须是 `SUBMIT/PENDING`。仅把单据状态改成审批中不能绕过提交节点。
- 审批通过和驳回需要当前角色对该面板拥有审批权限。
- BOM 等特殊面板的业务校验在状态写入前执行；失败时整个 `callButton` 事务回滚。

## 6. 选单与生单

单来源选单配置存于目标面板的 `selectConfig`；同一按钮组存在多个来源动作时使用 `selectConfigs`，键必须与动作名完全一致。每个来源可配置独立的 `source`、`condition`、`headerMap`、`detailKey` 和 `detailMap`。来源单查询必须限定为已审核，并与配置的附加条件合并；后端负责最终有效性检查。

推式生单由 `PxService.callButton` 分发到 `createXxxFromYyy`：

1. 校验来源单存在且状态允许。
2. 校验所需明细非空。
3. 映射目标表头和明细，并补齐必填默认值。
4. 通过 `insertGenerated` 创建目标草稿。
5. 返回目标 `panelCode` 和新编号供前端定位。

新增流转时不得只加前端按钮；必须同时加入服务端分支、来源状态校验、字段映射、编号前缀和回归测试。

来源明细保存来源面板、来源单号、来源行号和来源数量。后端统一防止重复选单、超量生单，并在审核、弃审或删除时重算来源累计报检、检验和入库数量。

## 7. 参照、单单据和报表

- 基础档案参照也通过 `/api/px/queryFormDataList` 查询，不建立前端本地选项副本。
- `metadata.singleDoc=true` 的档案只保存一张 `form_data`，数据行位于首个明细页签。
- `ReportPanelRegistry` 定义只读报表配置；`ReportQueryService` 从当前已生效业务单据构建报表行。
- 报表查询默认忽略草稿等未生效状态，分页上限由服务端控制。
- Dashboard 通过 `DashboardController` 聚合业务单据、待办、进度和档案统计。

### 门户通知聚合

- `/api/portal/badge` 和 `/api/portal/notice/list` 必须使用 JWT 中的当前账号，禁止返回全局演示数组。
- 待办来源是 `form_data.status='审批中'`，并按当前账号 `approvePanels` 过滤；标题、提交人和提交时间来自 `panel_config`、`form_data` 与最近的 `SUBMIT/PENDING` 审批记录。
- 审批消息来源是 `form_approval`。每次 `APPROVE` 或 `REJECT` 结果按同一单据最近一次 `SUBMIT` 的操作者确定接收账号，其他账号不得看到该消息。
- 库存预警复用 `ReportQueryService.currentStockRows()`，逐行检查库存状况表的 `现存量(主)`；严格小于 `500` 时产生预警，等于 `500` 不预警。
- 通知项返回 `panelCode`、`formNo`、`targetPath` 和 `actionLabel`，供前端直接定位审批单据或库存状况表。当前角标表示实时记录数；若后续需要跨设备未读状态，必须新增用户通知读取表和确认接口，不能用固定 `read` 值冒充持久化状态。

## 8. 身份、权限与错误

- `/api/auth/login` 和登录页所需的工厂列表允许匿名访问，其余接口需要 JWT。
- 密码使用 BCrypt；服务端无状态，不创建 HTTP Session。
- 管理员角色拥有全部面板和审批权限；普通角色由 `sys_role_panel` 控制可见面板和 `can_approve`。
- JWT 密钥必须由 `MES_JWT_SECRET` 覆盖，数据库凭据通过 Spring 环境变量注入。
- `IllegalArgumentException` 映射业务码 400，`IllegalStateException` 映射业务码 409，其他异常映射业务码 500；客户端同时检查 HTTP 状态和 `ApiResult.code`。
- 日志和异常消息不得输出密码、Token、Cookie、完整连接串或敏感业务数据。

## 9. 后端扩展清单

1. 确定功能属于通用 `PxService`、专属 Service 还是只读报表。
2. 先定义数据权威源和唯一键，再实现接口。
3. 写操作放入事务，校验发生在落库前。
4. 新面板同步 `panel_config`、`init.sql`、角色可见性和编号规则。
5. 新审批面板同步审批集合、状态矩阵和权限测试。
6. 新生单链路覆盖成功、来源未审核、来源不存在和明细为空场景。
7. 运行后端打包，并通过 `node tools/verify-project.mjs` 做整体验证。

## 10. 金额、库存与质量规则

- 金额字段的 `computed=true` 必须有完整 `calc` 公式。报价单统一计算“含税单价 = 报价单价 × (1 + 税率 / 100)”“金额 = 数量 × 报价单价”“含税金额 = 数量 × 含税单价”，并按配置精度做十进制舍入。
- 明细“现存量”以 `STOCK_STATUS` 为唯一口径：存在仓库字段时按仓库和存货汇总，不存在仓库字段时汇总该存货的全部仓库。不得把存货档案或来源单据中的静态值当作当前库存。
- 质量链路按 `ARRIVAL_IN/FINISH_INSPECT/FIRST_INSPECT/PROCESS_INSPECT_APPLY -> INSPECTION/PROCESS_INSPECTION -> PURCHASE_IN/FINISH_IN` 组织；`DISPATCH` 只可作为工序报检来源，不能代替 `PROCESS_INSPECT_APPLY`。
- `INSPECTION` 的检验数量、合格数量、不合格数量及不合格处理数量必须守恒，不合格处理引用 `REJECT`。已生成下游单据的来源单不得直接弃审或删除。
- 质量明细、统计、执行和追溯报表复用业务单据与来源关系，不另存一套可编辑业务数据。菜单、配置、种子和编号登记统一由 `QualityPanelRegistry`、`ReportPanelRegistry`、`PxService` 与 `init.sql` 共同维护。

## 11. PLM 领域落地原则

PLM 不是把 MES 面板改名。`panel_config` 负责页面描述，`form_data` 可承载低风险扩展字段或原型数据；产品身份、修订版、BOM 行、文档版本、基线和变更关系必须进入结构化领域表，并由独立 Service 维护事务与唯一约束。

初始领域边界应按需求逐项确认，候选对象包括 `Item`、`ItemRevision`、`DocumentRevision`、`BomLine`、`Baseline`、`ChangeRequest` 和 `ChangeOrder`。未确认的对象不提前建表。至少遵守：

1. 产品身份与修订版分离；业务引用指向明确修订版，不能只存显示名称。
2. 已发布修订不可原地覆盖；修改产生新修订并保留审计链。
3. BOM 行使用稳定主键和父子修订外键，数量、单位、生效区间及替代关系不可只存 JSON。
4. 文件二进制与元数据分离；数据库保存版本、校验值、存储引用和权限，不保存临时本机路径。
5. 签出、发布、变更执行和基线冻结属于领域动作，通过 `PanelActionHandler` 进入独立事务。
6. ECR/ECO 的状态机、审批角色、影响分析和回滚策略在实现前形成验收条件。
