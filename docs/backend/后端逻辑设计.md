# 轻 MES 后端逻辑设计

| 属性 | 内容 |
|---|---|
| 文档类型 | 后端设计 |
| 适用场景 | 后端逻辑设计 |
| 维护状态 | 生效 |
| 最后整理 | 2026-11-12 |
| 文档导航 | [文档中心](../README.md) |

本文描述当前 Spring Boot + PostgreSQL 16 后端（2026-11-12 由 MySQL 迁移，方案见 [数据库迁移](../deploy/数据库迁移-PostgreSQL.md)）。系统只保留 SQL 链路，不依赖外部 PanelX 服务，也不提供 Mock 运行模式。

## 1. 总体结构

```text
浏览器 /api/*
  -> SecurityConfig + JwtAuthFilter
  -> Controller
  -> PanelRuntimeService
  -> PxService + PanelActionHandler
  -> MyBatis-Plus Mapper
  -> PostgreSQL light_mes
```

| 层 | 主要实现 | 职责 |
|---|---|---|
| 配置与安全 | `config/` | JWT、Spring Security、CORS、分页和异常归一化 |
| 通用面板契约 | `panel/` | 运行时接口、动作上下文和业务 Handler 注册 |
| 接口 | `controller/` | 参数接收和统一 `ApiResult` 返回 |
| 业务 | `service/` | 面板 CRUD、审批、权限、生单、报表和 Dashboard 聚合 |
| 数据访问 | `mapper/`、`entity/` | MyBatis-Plus 实体与查询 |
| 初始化 | `resources/db/init.sql` | 建库、建表和新环境种子数据 |

## 2. 数据权威源

| 表 | 用途 |
|---|---|
| `panel_config` | 面板字段、列表、按钮、状态和选单配置 JSON |
| `form_data` | 通用单据表头 `data`、明细 `detail_data` 和单据状态 |
| `form_approval` | 提交、通过、驳回和弃审记录 |
| `sys_user`、`sys_role`、`sys_role_panel` | 用户、角色、可见面板和审批权限 |
| `sys_dept` | 组织树与用户归属 |
| `sys_menu`、`factory` | 门户菜单和工厂信息 |
| `manu_order`、`manu_order_item` | 传统生产加工单接口使用的结构化业务表 |

运行库是当前配置和数据的权威源；`init.sql` 是新环境初始化基线。修改运行库后，应把可重复的结构和配置同步回初始化 SQL，避免新部署与现有环境漂移。

`form_data` 的业务唯一键是 `(panel_code, form_no)`。表头和明细 JSON 必须保持以下边界：

```json
{
  "panelCode": "MANU_ORDER",
  "编号": "MO-...",
  "单据状态": "草稿",
  "detail": {
    "products": [],
    "materials": [],
    "processes": []
  }
}
```

### 预留扩展列（结构化业务表，30 个）

结构化业务表必须预留 30 个可空扩展列，新增业务字段直接占用空闲列，不为单个字段临时改表：

| 类型 | 列名 | 列定义 |
|---|---|---|
| 文本 | `ext_str1`～`ext_str10` | `varchar(200)` |
| 数值 | `ext_num1`～`ext_num10` | `numeric(18,4)` |
| 日期时间 | `ext_date1`～`ext_date5` | `timestamp(0)` |
| 标志 | `ext_flag1`～`ext_flag5` | `smallint`（实体映射为 `Boolean` 的列用 `boolean`，如 `stock_balance.ext_flag1`～`5`） |

- 当前覆盖 `manu_order`、`manu_order_item`；今后新建的结构化业务表在 `db/migration/V2__*.sql` 建表时按同一规则预留。
- 结构权威源是 `db/migration/`（Flyway）；`db/*.sql` 中的 MySQL 脚本只作回滚资产，不再演进。
- 新增字段优先写 `panel_config` JSON（普通面板字段不需要改表）；确需结构化字段时占用空闲 `ext_*` 列，并在实体字段注释和接口说明里标注「列 ↔ 业务字段」对应关系。
- 30 列用尽，或字段需要索引、唯一约束、外键时，先评估另建扩展表或改为 JSON 存储；确实要扩列，新增一个 Flyway 迁移一次预留新列批次，运行库不手工追加业务列。

## 3. 接口分组

| 路径 | 主要职责 |
|---|---|
| `/api/auth/*` | 登录、当前用户和权限 |
| `/api/px/*` | 通用面板配置、查询、表单描述、按钮动作和删除 |
| `/api/dashboard/stats` | Dashboard 聚合数据 |
| `/api/sys/menu/*` | 菜单树 |
| `/api/sys/user/*`、`/api/sys/role/*`、`/api/sys/dept/*` | 组织和权限管理 |
| `/api/manu/order/*` | 结构化生产加工单接口 |
| `/api/portal/*`、`/api/base/factory/*` | 门户角标、公告和工厂信息 |

`PxController` 只依赖 `PanelRuntimeService` 并做协议转换。当前 SQL 实现是 `PxService`：

- `getPanelConfig`：读取并升级运行时配置。
- `getPermMatrix`、`getNewFormPermMatrix`、`getFormDescriptor`：生成页面权限和表单描述。
- `queryFormDataList`：按面板分类查询普通单据、单单据档案或报表。
- `callButton`：在事务中处理保存、状态变化、审批和推式生单。
- `deleteForms`：按面板编码和单号删除。

通用生命周期未识别的按钮交给 `PanelActionRegistry`。一个动作只能匹配一个 `PanelActionHandler`；没有处理器或多个处理器同时匹配都立即失败。Handler 在 `callButton` 的事务中运行，可拥有自己的 Mapper 和领域 Service，禁止反向调用 Controller。

## 4. 创建和保存

1. 新建请求进入 `PxService.create/save`。
2. 后端按面板生成不重复的 `form_no`，并补齐单据日期、自动编号和配置默认值。
3. 新单状态默认为草稿；档案类面板按其启用规则保存。
4. 更新时以 `编号` 定位原记录。请求未携带明细时保留原 `detail_data`，禁止写成空值。
5. 保存前完成必填、编号、来源单和业务约束校验。

编号生成不得使用记录总数推算。新增前缀在 `PxService.generateFormNo` 登记，并依赖数据库唯一键处理并发冲突。

## 5. 状态与审批

```text
普通审核：草稿 --审核--> 已审核 --弃审--> 草稿
审批流程：草稿 --提交审批--> 审批中 --审批通过--> 已审核
                                  +--审批驳回--> 草稿
已审核/生产中 --手工完工--> 已完工
可执行状态 --中止--> 已中止 --取消中止--> 草稿
```

- 所有状态变化由后端再次校验，前端置灰不能代替服务端规则。
- 普通审核和审批流程互斥。启用审批的面板禁止“审核”直达已审核；兼容旧客户端时，旧“审核”动作按“提交审批”处理。
- 审批面板统一归一为一个“审批”组，动作顺序固定为提交审批、审批通过、审批驳回、审批情况和弃审。
- 提交、通过、驳回和弃审在同一事务内更新状态并写入 `form_approval`，操作人从当前 JWT 身份取得。
- 审批通过或驳回前，最近一条审批记录必须是 `SUBMIT/PENDING`。仅把单据状态改成审批中不能绕过提交节点。
- 审批通过和驳回需要当前角色对该面板拥有审批权限。
- BOM 等特殊面板的业务校验在状态写入前执行；失败时整个 `callButton` 事务回滚。

## 5.1 开放审批接口（只读，供 AI 助手轮询）

外部系统（当前是 doc-nexus-ai 的 AI 助手）需要知道「谁该审哪张单」。为此提供一个
**只读、独立令牌、按人查询**的接口，不复用用户 JWT。

| 事项 | 约定 |
|---|---|
| 路径 | `GET /api/open/approvals/approvers`、`GET /api/open/approvals/pending?approver=<账号>` |
| 鉴权 | 请求头 `X-Open-Api-Token`，值来自 `MES_OPEN_API_TOKEN` |
| 默认状态 | 关闭；`MES_OPEN_API_ENABLED` 非 true 时返回 404 |
| 来源限制 | `MES_OPEN_API_ALLOWED_IPS`，默认只允许 `127.0.0.1,::1` |
| 限流 | `MES_OPEN_API_RATE_LIMIT`，默认 120 次/分钟（按令牌计） |
| 方法 | 只有 GET；不注册任何写方法，从接口层杜绝篡改 |

**审批人口径复用 MES 自身**：`RoleService.getPerms(账号).approvePanels`，与门户待办
（`PortalNotificationService`）完全一致，不另立规则。待审单据取 `form_data.status='审批中'`
且在审批人授权面板内，提交人与提交时间回查最近一条 `form_approval` 的 `SUBMIT` 记录。

**返回字段白名单**（`OpenApprovalService.PENDING_FIELDS`）：

```text
panelCode, panelName, formNo, submitter, submittedAt
```

**刻意不返回**：单据正文、客户、金额、明细等业务字段。接口只回答「有什么要你审」，
要办事请登录 MES 打开单据，避免一把令牌带出整库数据。

**失败即拒绝**：未启用 404；启用但令牌为空 503；令牌缺失/错误 401；来源 IP 不在白名单 403；
超限 429。令牌用常量时间比较，错误信息不回显令牌。

配置只用环境变量，不入库、不进仓库：

```bash
MES_OPEN_API_ENABLED=true
MES_OPEN_API_TOKEN=<随机长串>
MES_OPEN_API_ALLOWED_IPS=127.0.0.1,::1
MES_OPEN_API_RATE_LIMIT=120
```

AI 侧配置在 `doc-nexus-ai/.env`：`MES_OPEN_API_ENABLED`、`MES_OPEN_API_BASE_URL`、
`MES_OPEN_API_TOKEN`（两侧令牌必须一致）。AI 侧规则与去重见 `doc-nexus-ai/docs/AI主动监控.md`。

## 6. 选单与生单

单来源选单配置存于目标面板的 `selectConfig`；同一按钮组存在多个来源动作时使用 `selectConfigs`，键必须与动作名完全一致。每个来源可配置独立的 `source`、`condition`、`headerMap`、`detailKey` 和 `detailMap`。来源单查询必须限定为已审核，并与配置的附加条件合并；后端负责最终有效性检查。

推式生单由 `PxService.callButton` 分发到 `createXxxFromYyy`：

1. 校验来源单存在且状态允许。
2. 校验所需明细非空。
3. 映射目标表头和明细，并补齐必填默认值。
4. 通过 `insertGenerated` 创建目标草稿。
5. 返回目标 `panelCode` 和新编号供前端定位。

新增流转时不得只加前端按钮；必须同时加入服务端分支、来源状态校验、字段映射、编号前缀和回归测试。

来源明细保存来源面板、来源单号、来源行号和来源数量。后端统一防止重复选单、超量生单，并在审核、弃审或删除时重算来源累计报检、检验和入库数量。

### 销售订单排产（生成生产加工单）

排产不是单据动作，而是生产准备：销售订单确定生产什么，排产决定怎么排。

```text
销售订单 SO-20261110-001（已审核）
  行1 CP005 ×10  ──排产──>  加工单 SO-20261110-001-1  CP005 ×10  工序=该产品工艺路线
  行2 CP002 ×30  ──排产──>  加工单 SO-20261110-001-2  CP002 ×30
  行3 CP003 ×200 ──排产──>  加工单 SO-20261110-001-3  CP003 ×200
```

- **一行一张加工单**：单号固定为 `销售订单号-行号`（行号按明细次序从 1 起），加工单表头同时写 `销售订单行号`，再次排产时据此计算该行剩余可排量。
- **可排数量按行算**：`订单行数量 − 该行已生成加工单占用`，不允许超出；同一产品在订单里出现多行时按行号区分，不按存货编码合并。老加工单没有行号字段时按「销售订单号 + 产品编码」认占用，且优先记到还有余量的行。
- **排产不审批**：加工单生成即已审核（内部走一次审批留痕），排产批次 `DISPATCH` 也生成即已审核，报工/领料直接可用。`DISPATCH` 已从 `APPROVAL_PANELS` 移除，面板上不再出现审批组。
- 排产时按产品工艺路线把工序写进加工单明细（`detail.processes`），并自动把首道工序排成批次；下道工序要等上道报工合格，回排产页继续排。
- 接口：`GET /px/saleOrderPlanBoard?saleOrderNo=` 看订单行可排数量；`POST /px/planFromSalesOrder` 生成加工单（`lines=[{行号,数量}]`，省略行=整单可排的每行）；加工单侧仍是 `GET /px/planBoard`、`POST /px/planBatch`、`POST /px/planAll`。
- **入口只有两处**：销售订单列表「排产」直接进订单行勾选；生产加工单列表「选销售订单」先弹窗列已审核销售订单，选中确认后进同一张排产界面对该订单勾行。不再有「一次把整张订单生成成一张多行加工单」的选单路径，加工单列表也没有「排产」按钮。
- **工序汇报单一道工序一张**：加工单点「生成工序汇报单」只带**当前该报的那道**——前道全部报满、本道还有余量；前道没报满时提示「前道工序要先报工完成」，全部报满提示「全部工序已全部报工」。
- **报工不审批**：工序汇报单（`PROCESS_REPORT`）已从 `APPROVAL_PANELS` 移除，加工单生单与按批次报工两条路径都建单即「已审核」，完工进度立刻生效；面板上不再有审批组。
- **成品报检单的生单只有两条**：生成产成品入库单、生成委外入库单。报检单本身就是检验结论（合格/不合格数量、检验结果都在明细里），不再生成检验单；也不再自己生成成品报检单。
- **成品检验单由成品报检单面板「选单 → 选生产加工单」生成**（与「生单」同一入口）：候选只给「全部工序报工完成 + 还没生成过报检单」的**生产加工单**（委外加工单仍走「选委外加工单」）。生成时表头直接写入 `单据日期`（当天）与 `单据编号`（= `<加工单号>-JY`），草稿就能看出是哪天报检、单号是什么；重复生成同一张加工单直接 409。：`GET /px/finishInspectCandidates` 只给「全部工序报工完成 + 还没生成过报检单」的加工单；弹窗勾选后逐张调用 `POST /px/finishInspectFromMo`，单号固定为 `<加工单号>-JY`，同一张加工单重复生成直接 409（提示已有报检单并给单号）。加工单侧的「生成成品报检单」保留，两个入口共用同一套校验与单号规则。
- **工序汇报的「选生产加工单」是专用弹窗**：`GET /px/processReportPickBoard` 给出「加工单 + 每道工序的计划/已报/未报/可否报工」，弹窗上表选加工单、下表选工序，只能选「本道未报满且前道都报满」的那道，报工数量默认未报数量；已报满标「已报满」、还没轮到标「前道工序还没报完」并置灰。确认后按 `POST /px/reportProcess` 生成一张只含该工序的汇报单（已审核）。不再走通用选单——通用选单会把整张加工单的工序一起带进来，撞「没有可执行数量 / 工序已全部报工」。
- **工序汇报单按加工单收成一格**：单据多了逐道展开会把流程拉得没法看，所以一张加工单的汇报单挂在同一个节点下，逐道工序作为分支（已报带单号、轮到未报写「生产中」、还没轮到写「待生产」），首件报检以二级标签跟在工序后面。
- **路线上的工序状态用生产口径**：已报工序显示汇报单与状态；轮到还没报的显示「生产中」；还没轮到的显示「待生产」。工序节点不是「少一张单据」，不写「待生成」。
- **加工单生单只有三条**：生成领料申请单、生成工序汇报单、生成成品报检单。
  - 领料申请单：材料明细按「计划数量 − 累计领用数量」带出，仓库取材料预出仓库，后面接材料出库单；
  - 成品报检单：**全部工序报工完成**才允许生成（未完成报「工序还没全部报工完成 x/y 道」），同一张加工单只建一张；
  - 产成品入库单不再从加工单直接生成，改由**成品报检单**生成：报检单必须已审核，底层仍按加工单累计入库量算剩余量；
    加工单侧另有「末道工序未报工完成」「首检/完工检验未通过」三道门兜底。
- **手工编号**：预生产新建加工单时勾「是否手工修改单据编码」，`加工单号`（字段 `锭号`）可自由填写，不套 `MO-yyyyMMdd-NNN` 规则，只校验唯一（`ManualDocNoRules`，重复报「生产加工单号已存在」）。不勾或留空仍按系统规则生成。

## 7. 参照、单单据和报表

- 基础档案参照也通过 `/api/px/queryFormDataList` 查询，不建立前端本地选项副本。
- `metadata.singleDoc=true` 的档案只保存一张 `form_data`，数据行位于首个明细页签。
- `ReportPanelRegistry` 定义只读报表配置；`ReportQueryService` 从当前已生效业务单据构建报表行。
- 报表查询默认忽略草稿等未生效状态，分页上限由服务端控制。
- Dashboard 通过 `DashboardController` 聚合业务单据、待办、进度和档案统计。

### 业务流程追踪（`/api/px/trace`）

- 入口单据任意：按「来源单号 / 销售订单号 / 匹配来源单号 / 加工单号」正反向 BFS，环不重复访问。
- 返回两部分：`steps` 是实际存在的单据；`route` 是**标准路线**，固定环节序列，未发生的环节 `是否已发生=false`、状态为「待生成」。
- 路线二选一，由**销售订单是否需要生产**决定：明细每一行的存货库存都不小于订单数量 → 直接出库（销售订单 → 销售出库单 → 销货单 → 销售发票）；任一行库存不足 → 生产路线（销售订单 → 工单排产 → 生产加工单 → 生产领料 → 材料出库单 → 工序汇报单 → 成品报检单 → 产成品入库单 → 销售出库单 → 销货单 → 销售发票，共 11 步；「生产领料」按排产批次直接生成材料出库单并提交审批，领料申请单只在「先申请后出库」的场景走）。有加工单时一律按生产路线。
- **排产在加工单之前**（2026-11-11 起）：先由销售订单排产生成加工单，排产批次（`DISPATCH`）随加工单产生，`PANEL_ORDER` 里 `DISPATCH` 权重小于 `MANU_ORDER`，所以追踪图上排产环节排在加工单前面。
- **流程图按订单行并行**（`lanes`）：一个销售订单行一条线，各走自己的排产 → 加工单 → 领料 → 出库 → 汇报 → 报检 → 入库；销售订单与出库/销货/发票是各线共用的头尾。一条线上的**排产只占一个节点**：一次排产就把该产品全部工序定下来，已排工序带批次单号、未开工的标「待生成」，工序挂在该节点下作分支，不再一道工序拆一个节点（`route` 里仍保留逐工序展开，用于环节计数与无排产线时的单行展示）。
- 库存口径取 `stock_balance` 现有量合计，不用销售订单行上的「现存量」快照。
- **工序派工单、工序汇报单按「工序 × 批次」展开**：一道工序可能排了多个批次（一批一张派工单、一张汇报单），同一工序的匹配单据全部展开、不合并；匹配用 `工序编码`（名称兜底），节点上带 `工序名称`。因此 3 道工序单批次渲染 11 + 2×2 = 15 个环节，多批次会更多；页面同时显示「N 步标准流程 · M 个环节」，骨架步数按面板去重统计。
- **首件检验单是工序汇报的分支**（`RouteNode.branches`），不占主干位置、不计入主干步数：**一道工序一张首检单**（明细只有本工序一行，带 `工序编码`/`工序名称`/`工序汇报单号`），按「加工单 + 工序编码」挂到对应工序汇报下。首检是报工门，未审核不能继续报工、不能转序。
- **成品报检单是完工检验门**：整单全面检验，未审核不能生成产成品入库单（`requireFinishInspectApproved`，与首检放行同一套写法；无工序路线的老单不限制）。
- **现场领料直接出库、但要审批**（2026-11-12）：`POST /px/issueBatch` 按排产批次一次性领多种材料，落一张多行 `MATERIAL_OUT`（来源单据 = `DISPATCH`，明细行带 `排产单号`），**不走领料申请单**；生成立即提交审批（`submitIssueForApproval` → `submitApproval`，单据状态直接进「审批中」），提交失败会把半张草稿删掉，避免草稿被看板当成「可再领」。库存只在审批通过时落 `stock_txn`（实测：审批后 CL001 原料仓 5752.83 → 5746.65、CL004 辅料仓 296.98 → 296.78）。**一个批次同时只允许一张在途出库单**：`blockingIssueOfBatch` 命中「审批中 / 已审核」就拒绝再次领料，驳回退回草稿后可重领。
- **领料看板带出库状态**：`materialIssueBoard` 每行返回 `出库单号` / `出库状态`（未领料 / 草稿 / 待审批 / 已审批 / 已驳回）与 `可否领料`（有剩余量 且 无在途单或已驳回）；驳回的判定看 `form_approval` 里该单最新一次动作是不是 `REJECT`。
- **成品报检单按「入库单状态」筛选**（2026-11-12）：`queryFormDataList` 查 `FINISH_INSPECT` 时按加工单号带上同一张加工单的产成品入库单（`finishInByManuOrder`，一次建索引不逐行查），行上多一个桶字段 `入库单状态`：未转入库单 / 入库单审批中 / 入库单已审批 / 入库单已驳回 / 入库单草稿（驳回判定看 `form_approval` 最新动作 `REJECT`）。`condition` 里的 `入库单状态` 走专用匹配 `matchIssueBucket`：**「转入库单」= 除未转以外的全部**，「未转入库单」与其余桶按相等；其余字段仍是包含匹配。
- **看板「未开工」= 还没排产的工序**（2026-11-12）：`GET /px/pendingPlanBoard` 逐个已下发加工单（状态 已审核 / 生产中）调 `planBoard`，只留可排产量 &gt; 0 的工序行，去掉其中的批次列表；可排产量 = 上道合格量 − 已审核排产量，所以中止批次释放出来的量会自动回到这一列。前端看板据此三列归类：未开工（工序 + 可排量，虚线卡）/ 生产中（已审核批次且剩余 &gt; 0）/ 完工（剩余为 0）。
- **首件在前、报工在后**（2026-11-12 二次调整，取代 11-11 的「报首件量再检」）：首检是报工的**前置条件**，不是报工的副作用。该工序没有「已通过」的首检单时，任何批次都不许报工（`validateBatchReport` 直接拒绝，报错点名工序与首检单状态）；首检单在工作台点「生成首件报检单」补建（`POST /px/firstInspectByBatch` → `createFirstInspectByBatch`），已存在则原单号返回，不重复建。判据是 `PxService#firstInspectOf(加工单号, 工序编码)`：**一工序一单，同工序的后续批次共用同一张首检单**，作废不算。报检数量取「首件样本量」（工序 `首检数量`，缺省 1），受批次剩余量封顶。
- **首检状态跟着批次走**：`reportBatchBoard` 每行带 `首检状态`（未建单 / 待审批 / 不合格 / 已通过）、`首检单号`、`首检是否通过`，`可否报工 = 剩余量>0 且 首检已通过`，`不可报工原因` 按「批次已报满 → 首检未建 → 首检待审 → 首检不合格」的优先级给具体文案（`firstInspectBlockReason`）；首检单一次全量取，按加工单建索引，避免逐行查库。
- 入库端保留兜底门：每道工序都要有**已通过**的首检单（`requireFirstInspectApproved`，无工序明细的老单按「有首检单就必须审过」判定）；末道全部完工仍单独用于判定「可以入库」。
- **首检单走两段审批、判定必填**（2026-11-11 起）：`FIRST_INSPECT` 收进 `APPROVAL_PANELS`，按钮组换成「提交审批/审批通过/审批驳回/审批情况/弃审」，与成品报检同口径；明细新增「检验判定」（合格/不合格/让步接收，无默认值）、「处置方式」（返工/返修/让步接收/报废）、「处置数量」、「判定说明」，`validateFirstInspectVerdict` 在提交与审批时都校验：判定必填，判定=不合格时处置方式必填、处置数量必填（让步接收除外）。
- **不合格处置怎么驱动流程**：放行判据是 `已审核 且（判定≠不合格 或 处置=让步接收）`。判不合格后按处置分流——返工/返修 → 该工序继续锁死，在工作台再点「生成首件报检单」会开一张重新首检单（明细回填「原首检单号」，联查靠 `LINK_KEYS` 里的原首检单号串回原单），重检合格才放行；让步接收 → 留痕放行；报废 → 不自动重检，报工直接拒绝并提示走返工/补投加工单，同时该数量从可入库量里扣掉（入库预览与生成入库单都按 `计划 − 已入库 − 报废` 计算，预览弹窗多一列「报废」）。
- **P0 三道门（2026-11-12）**：① 报工前置——该加工单必须已有已审核材料出库单（`requireMaterialIssued`，开关 `mes.production.require-material-issue`，默认开），杜绝用"黑料"生产；② 成品报检前置——全部工序首检通过才允许生成（`requireAllFirstInspectionsPassed`，报错点名卡住的工序与单号）；③ 返工/补投生产加工单——面板按钮原先没有后端实现（点了报「未定义按钮规则」），现按首检处置=报废的数量生成，数量口径只有一处（`scrappedQtyByProduct`），已开单的报废量按未作废返工/补投单抵扣，避免同一批报废件反复开单。
- **领料申请单的产品归属（2026-11-12）**：加工单材料行带「子件BOM」= 产品编码；老加工单没带就按物料清单「子件编码 → 父件编码」反查，还不唯一时退回唯一产品；产品名称按编码回查物料清单父件名，不再写空串。领料数量按「计划数量 − 累计领用数量」带剩余量（BOM 展开与损耗在产品数量 × 单件用量时已算进加工单材料行）。面板明细与列表补「材料编码」列（`MaterialReqPanelUpgrade` 启动时幂等补齐），仓库能按编码区分同名材料。**倒冲料不进领料申请单**：投料方式含「倒冲」且不是「不倒冲」的材料在生单时直接剔除（它们由 `backflushMaterials` 在报工时按「累计报工 × 单件定额 ×(1+损耗率)」自动补材料出库，来源标「报工倒冲」）；全部材料都是倒冲料时直接提示不需要领料单，避免生成一张必定被 `assertNoBackflushReqItems` 拦下的废单。
- **工程变更（ECR/ECO）落地（2026-11-12）**：PDM 此前只有主数据（存货/BOM/工艺路线），没有「谁改的、改了什么、现在第几版」的记录。新增 `ENG_CHANGE` 工程变更单（表头：申请人/变更原因；明细：对象类型 物料清单|工艺路线、对象编码、变更级别 大/小版本、说明），审核后由 `POST /api/px/eng/apply` 执行：按对象找到目标单据（工艺路线按表头编码；物料清单先表头产品编码、再明细物料清单编码），把 `版本号` 进位（小版本 V1.0→V1.1、大版本 V1.0→V2.0），并写 `变更单号` 与 `最后变更日期`。`EngChangePanelRegistry` 启动时给 BOM/ROUTE 表头幂等补这三个字段。任一行找不到目标就整单拒绝（事务回滚），不留半截改版。已知边界：加工单尚未记录所用 BOM 版本，「变更追溯到具体生产订单」还需在加工单上带版本戳。
- **仓内作业层落地（2026-11-12）**：此前仓内只有单据 + 一张只读的「拣货工作台」报表——任务是查询时现算的，拣了多少、上架到哪个货位、复核过没有都无处存。新增 `wms_task` 表与 `WmsTaskService`：① 从已审核出入库单**幂等同步**任务（唯一键 `类型+来源面板+来源单号+行号`，重复同步不造重复任务，也不覆盖现场进度）；② 拣货/上架**确认作业量**（覆盖式，超计划量直接拒绝；上架完成必须填目标货位），状态按 待作业/部分完成/已完成 推进并记完成时间；③ **编波次**按仓库把待拣任务归到 `W-日期-序号`（已编波不重编）；④ **复核**按来源单号给整单任务写结论（已复核/有差异）。库存口径不变：库存仍只由单据审核落 `stock_txn`；上架任务的货位是现场记录，要真正挪库存货位用「货位调整单」（已按 原货位 OUT + 新货位 IN 落账）。接口在 `/api/px/wms/*`，页面 `/wms/workbench`。
- **仓内作业三张单的落账口径（2026-11-12）**：`StockTxnService#post/reverse` 原先把 `directionOf(panelCode)` 当闸门，只有单方向出入库面板能落账——调拨单是「一出一进」没有单一方向，`buildTransferTxns` 写好了却永远走不到，审核直接返回 0（实测：调拨单审批通过后 `stock_txn` 0 条、库存不动）。现改为 `postsStock(panelCode)` 统一判断：调拨每行落「调出仓 OUT + 调入仓 IN」；**库存盘点单审核即按盈亏调账**（盘盈 IN / 盘亏 OUT，缺 `盈亏数量` 时按 实盘−账面 兜底，金额取结存均价）；**货位调整单**每行落「原货位 OUT + 新货位 IN」，数量与仓库不变，原货位有值时先校验该货位可用量，避免手填错货位把库存扣成负数。弃审按「面板 + 单号」冲销，重审可自愈。
- **倒冲的四个现场条件（2026-11-12）**：① 库存校验——`requireBackflushStock` 在报工时按「本次报工量 × 单件定额 ×(1+损耗率) − 已倒冲」逐料校验目标仓可用量，不够直接拒绝报工；`createBackflushMaterialOut` 出库前再校一次，任何一条不够就整单不出（绝不把库存扣成负数）。② 线边仓——材料行填「线边仓」后倒冲扣线边仓；线边仓不够时自动开调拨单从「预出仓库」补料（`TRANSFER` 现在会落两条库存事务：调出仓 OUT + 调入仓 IN）。③ 批次——材料行「批次号」随倒冲/差异单据带进库存事务，`stock_balance` 按批次分账。④ 差异与例外——材料行「实际消耗数量」配合「倒冲差异调整」动作：实际大于已倒冲 → 材料出库（倒冲差异补扣），小于 → 其他入库（倒冲差异回冲）；「不可倒冲」勾上后该料不再自动扣、转人工领料。
- **全倒冲加工单豁免领料门**：`hasManualIssueMaterial` 为 false（材料全部是倒冲料）时，`requireMaterialIssued` 不再要求已审核材料出库单，否则这类加工单永远报不了工。
- **一来源一单（2026-11-12）**：`findExistingMaterialOut` 按「来源单据 + 来源单号」查未作废的材料出库单，草稿也算已生成——同一张领料申请单/调拨单/加工单只允许一张材料出库单，重复生成会被直接拒绝并提示已有单号与状态。此前只校验「剩余量」，草稿不联动又不挡重复，两张都审核就会多扣一倍库存。
- **排产批次 = 只读看板 + 流程图上的数据监控节点（2026-11-12）**：派工单不需要人操作、也不走审批（生成即已审核）。菜单「生产管理 → 排产批次看板」（`/mes/dispatchBoard`）提供只读看板：在制/完工批次、派工与已报数量、完成度、可否报工；原「工序派工单」面板退出菜单，只在联查与报工工作台的批次链接里出现（容量调整用的「中止（释放未执行量）」仍在该面板上，属高级操作）。业务总览的生产流程图里，排产批次渲染为虚线「监控」节点，不计入环节数、不作为流程环节（流程环节 = 需要人操作的步骤）。
- **排产批次的可操作项（2026-11-12）**：派工单面板是批次载体，只保留「查看进度 / 中止 / 取消中止 / 联查」；报工与材料出库的生单入口已摘除（点了只会报错）。「中止（释放未执行量）」= 把该批次未报工的数量放回可排产量（批次置「中止」，`planBoard` 不再计入已排产量），用于按产能动态调整——先把自动排的整批释放，再按实际产能分几次 `planBatch`（排产对话框可改数量）。
- **路线图里「生产领料」不再是节点**（2026-11-12）：`MATERIAL_REQ` 既不进 `PRODUCTION_ROUTE`，也不作为「模板外单据」补进路线（`steps` 里仍在，单据清单照常能查到）；环节之间的**流转动作**由前端标在箭头上（`MANU_ORDER>MATERIAL_OUT` = 「生产领料」）。同时排产节点按**批次**展开分支（`planNode` 一道工序多个批次全部列出，中止的写「已中止」），没有批次但已报过工的老路径工序写「无批次报工」（不再是「待排产」）；并行线里分批报工的汇报单也全部列成工序分支；主干汇总视角的工序清单按工序编码去重，避免多张加工单的同名工序多出一个空的「待生成」节点。
- **追踪模板与现场领料对齐、中止批次不算卡点**（2026-11-12）：`ProcessTraceService.PRODUCTION_ROUTE` 去掉 `MATERIAL_REQ`——现场领料直接出材料出库单，领料申请单只在「先申请后出库」场景出现，出现在 `steps` 里时按模板外单据插到正确位置，不再永远差一个「待生成」环节。`stateOf` 把「中止」也落成「已中止」（原来只认「已中止」，中止的批次被画成进行中）；`detectStalled` 跳过 `中止` 的 DISPATCH——那是我方主动调产能、未执行量已放回可排产量，不是流程卡住。- **流程图跟着批次走（2026-11-12）**：业务总览的工序汇报节点下，每道工序分支的第一个标签是「工单排产 + 批次号（PG-xxx）」，未排的工序标「工单排产 待生成」，随后才是「工序汇报 GX-xxx」与「首件报检单 SJ-xxx」。这样图上能直接看出「先排批次 → 按批次报工 → 首件检」的顺序，符合 A 方案的强制关系。
- **报工改为按排产批次（2026-11-12，A 方案）**：报工唯一入口是「工序报工」工作台（`/mes/processReport` → `reportByBatch`），必须先排产并审批；加工单上的「生成工序汇报单（自制汇报）」按钮已下线（配置启动时摘除），对已排批次的加工单直接调该动作会被拒绝并提示去工作台。首件门跟随工序走：该工序还没有「已通过」的首检单时不许报工（同工序的首个批次检过，后续批次直接放行；工作台里可一键补建首检单并跳过去）；报工同样触发 `afterProcessReportApproved`（进度/套数/倒冲）。材料领用按批次：`createMaterialReqFromMo` 按材料的「领料工序编码」匹配已审核排产批次，把「排产单号」写进领料明细，材料出库据此按批次控量。
- **多账号实测暴露并修掉的四处（2026-11-12）**：① 加工单已完工后不能再入库/成品报检（`已完工` 不在状态白名单里，最后一批货入不了账）——白名单补上 `已完工`；② 报工免审批路径没有推进批次累计/加工单进度/倒冲料（只有审批路径 `markAudited` 调了 `afterProcessReportApproved`），生单后补调，否则成品报检会被「累计完工量 0」拦住；③ 报工联动生成首件报检单时走了带权限校验的 `insertGenerated`，车间账号报工直接 403——改为 `insertGeneratedSystem`（系统联动单据不校验目标面板新增权限）；④ 追踪把「作废」单据当成流程中断（`已中止`）报卡点，作废单直接跳过。
- **待修**：销售订单排产（`planFromSalesOrder`）只建加工单，`planAll` 在同一事务内拿不到刚建的加工单看板数据，导致**排产批次没落**，追溯图上「工单排产」环节永远显示待生成；且加工单完工后不允许再排产，事后无法补。下一轮应改成建完加工单后单独触发排产（或直接按工序创建批次）。
- 委外加工单没有工序明细，按产成品的工艺路线带出工序：点「生成委外入库单」时缺哪几道就补建哪几道首检单，并一次性报出补建清单，审完才能入库（`requireOutsourceFirstInspects`）。
- **委外链补齐（2026-11-12 实测后）**：
  ① 首检门补建的单据必须在**独立事务**里落库（`inNewTransaction` / `PROPAGATION_REQUIRES_NEW`）——原来是同一个事务，抛出「已补建 3 张首检单」的拦截异常会把刚建的单据一起回滚，结果点一次建一批、再点又建，委外入库永远过不了这道门；
  ② 委外发料单 `OUTSOURCE_ISSUE` 进 `StockTxnService.OUTBOUND_PANELS`，审批按明细行**逐行仓库**出库；此前不在出库集合里，委外只进不出；
  ③ 发料行仓库改走 `pickIssueWarehouse`：预出仓有存量用它，没存量退到该物料实际有存量的仓（`warehouseOfItem`），都没存量才用预出仓/兜底——避免「预出仓写原料仓、料其实在辅料仓」扣成负库存；
  ④ 应付**只由委外加工费用单**确认（`FinanceSettleService.PAYABLE_PANELS` 去掉 `OUTSOURCE_IN`），金额取明细「费用金额」、往来单位取「委外供应商」；入库只落库存不记 AP，否则一笔加工费在入库单和费用单各记一次；
  ⑤ 凭证模板补 `OUTSOURCE_FEE`：借 5001 生产成本 / 贷 2202 应付账款；`settlementAmount` 补「费用金额」字段，否则分录金额算成 0 只出 AP 不出分录。
  ⑥ **入库成本口径**：委外入库单金额 = 材料成本（发料材料**结存均价 × 计划用量**）+ 加工费（委外单价 × 数量），多产成品按数量占比分摊材料成本（`outsourceInboundAmount` / `apportionOutsourceMaterialCost`）；发料单行也按结存均价带出单价与金额，否则出库成本为 0、两侧对不上；
  ⑦ **委外追踪路线**：`ProcessTraceService` 新增 `OUTSOURCE_ROUTE`（销售订单 → 委外加工单 → 委外发料单 → 委外入库单 → 委外加工费用单），按模板下标排序（`PANEL_ORDER` 是生产链口径，会把首检排到入库之后）；
     **追踪范围只圈被追踪那张委外加工单自己的链**（`onOutsourceChain`：销售订单 + 该加工单 + 来源单号指向它的单据），同一销售订单下的兄弟委外单与自制线（排产/加工单/领料/报工/成品入库）都不进这条路——实测修正前一次追踪 33 个环节；
     **回厂首检单作为委外入库节点的分支**（一工序一张，`outsourceInspectBranches`），不再各占一格。
  ⑧ **采购追踪路线**（2026-11-12）：新增 `PURCHASE_ROUTE`（请购单 → 采购订单 → 到货单 → 检验单 → 采购入库单）。采购单不再套销售直发模板，原先会凭空多出「待生成 销售出库/销货/发票」三个环节；
     **分批到货收成一个节点 + 分叉**（`BATCH_PANELS`：到货单、检验单一次一张，多张合并，首批带单号、其余挂分支）；
     入库单已存在却没有检验单时，检验环节写「**免检直入**」而不是「待生成」（到货行免检直接从到货单进的库）。

- **检验单只处理到货单（2026-11-12 收口）**：来料与**委外回厂**都是「到货单收进公司」，所以 `INSPECTION` 的唯一来源是到货单——
  「选单」下拉只留「选到货单」，`selectConfigs` 也只有这一项；首件报检单不再「生成检验单」（它自带判定与处置），
  成品报检单本来就不推检验单。**业务类型/检验类别只留「来料检验 / 委外检验」**，成品检验由成品报检单承载。
  生单三选一（由检验判定与现场去向决定）：`生成采购入库单`（合格回原料仓）、`生成委外入库单`（委外回厂）、
  `生成采购退货单`（判定退回/报废）；`生成产成品入库单`、`生成成品报检退回单` 两个成品侧入口从检验单摘除，
  `requireInspectionInboundTarget` 对 `FINISH_IN` 直接拒绝并提示走成品报检单，非到货来源的检验单不许转采购/委外入库。
  到货明细全为免检物料时，「生成检验单」拒绝并提示直接「生成采购入库单」（免检直入），这也是追踪里检验环节显示「免检直入」的由来。

- **到货单的「来源类型」决定能生哪种入库单（2026-11-12）**：到货单表头新增 `来源类型`（采购 / 委外，默认采购），
  来源自动带上——采购订单生单写「采购」，**委外加工单新增的「生成到货单」**写「委外」（业务类型=委外回厂、供应商=委外供应商、仓库=成品仓）；
  检验单由到货单生成时把 `来源类型` 复制过来。
  入库入口按它互斥（`requireArrivalInboundTarget`）：采购到货只能 `生成采购入库单`，委外回厂只能 `生成委外入库单`（到货单生单组新增该入口），
  生错直接 409 并点明该用哪个按钮；检验单转库时同样按 `来源类型` 拦（采购→采购入库、委外→委外入库）。
  老单据没有这个字段时按「采购」处理，不影响历史数据。

- **序列号管理跟着单据走（2026-11-12）**：原来「序列号登记单 + 状况表/跟踪表」是一张孤立的登记单，没有任何业务写入方，
  运行库 0 行、状况表永远空。现在改为：
  ① 存货档案（`INV`）加 `序列号管理`（是否）与 `序列号管理方式`（入库登记/出库核销）；
  ② 入库单（采购入库/产成品入库/委外入库/其他入库）加「序列号」明细页签，审核时登记；
  ③ 出库单（销售出库/材料出库/其他出库）加同名页签，审核时核销；
  ④ 状况表只列在库、跟踪表带出入库单号，两者都由 `SerialNumberService#aggregate` 从单据明细**实时聚合**，弃审即回滚，不再落第二份台账；
  ⑤ 审核硬校验（`SerialNumberService#validate`，在改状态**之前**执行，否则本单会被自己算成已登记）：数量与序列号一一对应、
     单内不重复、同一存货全局唯一、出库序列号必须「在库」且属于该存货；只有**已审核**单据才算登记/核销（草稿不占号）。
  ⑥ `SERIAL_NO` 登记单退化为「历史补录/导入」入口，从审批面板清单里摘除，明细本身就是序列号行。
- 比入口单据更上游的环节不补「待生成」，避免从加工单追踪时出现「待生成 销售订单」；模板之外的关联单据（调拨、过程检验等）仍按业务顺序插回。

### 检验数量约束（合格 + 不合格）

- 成品报检单明细：`合格数量`、`不合格数量` 必须落在 `[0, 报检数量]`，且两者之和不能超过 `报检数量`；检验结果不是「待检」时二者之和必须**等于**报检数量。
- 校验两道：草稿**保存时**就拦（不用等到提交审批），审批前 `validateQualityForApproval` 再走一遍；报错文案带行号。
- 前端同样夹住：表单联动（`core/inspection-qty.js`）和列表内联编辑都会把越界值压回，避免出现「报检 10、合格 11、不合格 -1」这种可见的错误状态。

### 字段布局（顺序 / 列宽 / 显隐，全公司共用）

- 存储表 `px_column_pref`，`owner=''` 表示全公司共用的一套；个人行（legacy）仍优先，没个人行才用共用行。
- `GET /px/fieldLayout?panelCode=` 返回表头 + 各明细页签全部字段的 `序号/列宽/显示`；`POST /px/saveFieldLayout` 保存（整体替换）。
- **是权限功能**：保存需要该面板的「调整」权限（`adjust`，管理员默认有），普通用户只能看效果不能改。
- 生效范围：列表页 gridTabs 列的顺序与显隐、列宽（`metadata.columnPrefs[].width` → 表格 `width`）；明细页签字段顺序与显隐同源。
- 列宽限制 40–800 px，越界直接拒绝。

### 门户通知聚合

- `/api/portal/badge` 和 `/api/portal/notice/list` 必须使用 JWT 中的当前账号，禁止返回全局演示数组。
- 待办来源是 `form_data.status='审批中'`，并按当前账号 `approvePanels` 过滤；标题、提交人和提交时间来自 `panel_config`、`form_data` 与最近的 `SUBMIT/PENDING` 审批记录。
- 审批消息来源是 `form_approval`。每次 `APPROVE` 或 `REJECT` 结果按同一单据最近一次 `SUBMIT` 的操作者确定接收账号，其他账号不得看到该消息。
- 库存预警复用 `ReportQueryService.currentStockRows()`，逐行检查库存状况表的 `现存量(主)`；严格小于 `500` 时产生预警，等于 `500` 不预警。
- 通知项返回 `panelCode`、`formNo`、`targetPath` 和 `actionLabel`，供前端直接定位审批单据或库存状况表。当前角标表示实时记录数；若后续需要跨设备未读状态，必须新增用户通知读取表和确认接口，不能用固定 `read` 值冒充持久化状态。

## 8. 身份、权限与错误

- `/api/auth/login` 和登录页所需的工厂列表允许匿名访问，其余接口需要 JWT。
- 密码使用 BCrypt；服务端无状态，不创建 HTTP Session。
- 管理员角色拥有全部面板和审批权限；普通角色由 `sys_role_panel` 控制：`perms` 列保存逗号分隔的权限码，`can_approve` 由是否含 `audit` 派生（存量空 `perms` 回退为 `view[,audit]`）。
- 权限码共 11 项：`view/query/add/edit/delete/export/print/audit/price/review/adjust`（`review/adjust` 为预留位，暂无受控按钮）；按钮名与权限码的映射表是 `PxService.ACTION_BUTTONS`，`生成*` 前缀按 `add` 处理。
- `/api/auth/login`、`/api/auth/userinfo` 与 `/api/auth/perms` 输出 `panelPerms`（面板 → 权限码数组；管理员为空 map 表示不拦截）；前端在渲染层用它过滤按钮组，后端 `/api/px/getPermMatrix` 同时按登录用户过滤 `visible/operatable` 作为契约输出。
- 前端按钮过滤不是授权边界：`/api/px/*` 与 `/api/manu/order/*` 在服务端按 `view/query/add/edit/delete/audit` 再次校验；生单还要求目标面板的 `add` 权限，扫描填单要求来源面板的 `add` 权限。未授权请求返回业务码 403。
- 前端请求层必须把 HTTP 200 中的业务码非 200 响应当作失败；权限不足只提示，不得清除登录态，只有 HTTP 401/403 才跳转登录。
- `panel_config.module_group` 保存模块分组（13 组），组织架构页的分组来自后端 `/api/auth/perms` 的 `modules`，不在前端硬编码。
- JWT 密钥必须由 `MES_JWT_SECRET` 覆盖，数据库凭据通过 Spring 环境变量注入。
- `IllegalArgumentException` 映射业务码 400，`IllegalStateException` 映射业务码 409，其他异常映射业务码 500；客户端同时检查 HTTP 状态和 `ApiResult.code`。
- 日志和异常消息不得输出密码、Token、Cookie、完整连接串或敏感业务数据。

### 表格列定制（px_column_pref）

- 用户级表格列定制存 `px_column_pref`（`panel_code + owner` 维度，每列一行：`seq` 顺序、`alias` 栏名别名、`visible` 显隐）；无行即默认列序。
- 叠加发生在 `getPanelConfig(panelCode, userName)` 读取出口：按 `seq` 重排 `metadata.panelPageDto.tablePages[].gridTabs[].columns`（兼容字符串列与对象列，未收录列按原序追加）、剔除 `visible=0`，并注入 `metadata.columnAliases`（列名→别名）与 `metadata.columnPrefs`（全量清单，含隐藏列）。
- 绝不把定制写回 `panel_config.config`——4 个 Registry 启动时会无条件覆盖该列。
- `POST /api/px/saveColumnPrefs` 保存（`columns` 空数组 = 恢复默认，删除该用户该面板全部行）；别名重复在服务端校验拒绝。
- 引擎兼容：`PanelRuntimeService` 以 `default` 方法扩展 `getPanelConfig(panelCode, userName)` 与 `saveColumnPrefs`，其它实现不受影响；`engine.buildRefCondition` 探测的是 `metadata.buttonGroups` 的审核按钮，不受列重排影响。

### 界面语言与机器翻译（sys_locale / sys_translation）

- 界面词条翻译只做显示层：`GET /api/locale/list` 返回 `sys_locale(enabled=1)` 注册表（`zh-CN` 恒首位），`POST /api/locale/dict` 按 `{locale, keys}` 返回词条字典。
- `TranslationService` 三级来源：内存缓存（30s TTL）→ `sys_translation(scope='biz')` 库表 → 阿里云机翻（`com.aliyun:alimt20181012`，`scene=general`，`zh→目标语言`）；机翻成功 `INSERT ... ON DUPLICATE KEY UPDATE` 落库。
- 机翻失败或凭证未配置（`mes.mt.*`，默认与 OCR 共用 `ALIBABA_CLOUD_*`）不返回该键，前端 `tt()` 回退中文原文；单请求键数上限 50。
- `localeKey` 归一：`zh-TW/HK/MO → zh-TW`，其余取主语言小写（`en-US → en`）；`zh*` 源语言直接短路返回空字典。

### AI 数字员工单点登录（/api/ai/sso-ticket）

- 顶栏「AI 数字员工」按钮走免密进场：`GET /api/ai/sso-ticket`（需登录）返回 `{ticket, url}`，前端在新标签打开 `url`，AI 侧建会话后 302 到 `/chat`。
- 票据格式两端一致（light-mes `AiSsoService` / doc-nexus-ai `app/services/mes_sso.py`）：`base64url(payload) + "." + base64url(hmac_sha256(secret, base64url(payload)))`，`payload = {sub:账号, name:姓名, role, admin, iat, exp, jti}`，有效期 60 秒。
- 共享密钥由两侧环境变量注入且必须相同：light-mes `MES_AI_SSO_SECRET`、doc-nexus-ai `DOC_NEXUS_MES_SSO_SECRET`。**留空即关闭该入口**：`/api/ai/sso-ticket` 返回 503，前端回落到「只打开对话页」（`MES_AI_BASE_URL` 默认 `http://localhost:18091`）。
- AI 侧验签通过后走 `mes_auth.sync_user` 镜像本地用户（MES 是账号与权限的权威源，密码不落库），再签自己的 access_token 与 `doc_nexus_refresh` cookie；SPA 启动时的 `POST /auth/refresh` 用 cookie 恢复会话，因此前端产物无需改动。
- 残余风险：票据在 60 秒内可重放（未做服务端一次性登记）。它只经一次浏览器跳转、只用于内网，票据泄露的窗口由此局限；如要彻底消除，需在 MES 侧加 `jti` 登记表并在 AI 侧回调核销。
- 已知限制：AI 前端只有编译产物（`doc-nexus-ai/frontend/dist`），本特性只改其后端，避免改 chunk。

2. 先定义数据权威源和唯一键，再实现接口。
3. 写操作放入事务，校验发生在落库前。
4. 新面板同步 `panel_config`、`init.sql`、角色可见性和编号规则。
5. 新审批面板同步审批集合、状态矩阵和权限测试。
6. 新生单链路覆盖成功、来源未审核、来源不存在和明细为空场景。
7. 运行后端打包，并通过 `node tools/verify-project.mjs` 做整体验证。

## 10. 金额、库存与质量规则

- 金额字段的 `computed=true` 必须有完整 `calc` 公式。报价单统一计算“含税单价 = 报价单价 × (1 + 税率 / 100)”“金额 = 数量 × 报价单价”“含税金额 = 数量 × 含税单价”，并按配置精度做十进制舍入。
- 明细“现存量”以 `STOCK_STATUS` 为唯一口径：存在仓库字段时按仓库和存货汇总，不存在仓库字段时汇总该存货的全部仓库。不得把存货档案或来源单据中的静态值当作当前库存。
- 质量链路按 `ARRIVAL_IN/FINISH_INSPECT/FIRST_INSPECT/PROCESS_INSPECT_APPLY -> INSPECTION/PROCESS_INSPECTION -> PURCHASE_IN/FINISH_IN` 组织；`DISPATCH` 只可作为工序报检来源，不能代替 `PROCESS_INSPECT_APPLY`。
- `INSPECTION` 的检验数量、合格数量、不合格数量及不合格处理数量必须守恒，不合格处理引用 `REJECT`。已生成下游单据的来源单不得直接弃审或删除。
- 采购退货按来源分流库存方向：检验退料（来源检验单、未入库）不写 `stock_txn`，库存退料（来源采购入库单）写 OUT；退货行金额按本次退货数量 × 来源单价/含税单价折算，部分退货不得整行复制来源金额。
- 混杂到货单：检验方式=免检的行不送检，仍可从到货单直入；非免检行必须先由检验单接手。来料检验只能生成采购入库单，成品/委外检验只能生成产成品/委外入库单。检验明细的处置相关字段变化并保存草稿时，原「确认处置」自动回退「待确认」。
- 检验单数量口径：报检数量 ≥ 应检数量 ≥ 检验数量；合格 + 不合格 = 检验数量。不合格处理页签的退回数量同时回写「验收退回数量」（对外）与「判定退货数量」（历史兼容），退货上限优先取验收退回数量。让步接收含税单价按原含税单价 ×（1 − 折价率）回写，纯让步接收行入库按该价结算。
- 检验项目页签 `projects`（来料/成品检验单、生产过程检验单）：关联明细行号、检验项目编码/项目、检验内容、检验标准、标准上下限、检验结果、单项判定（合格/不合格）、检验时间/检验员、备注。单项判定不合格时，该主行检验结果判定不能为合格；关联行号必须落在明细范围内。
- 生产过程检验单 `PROCESS_INSPECTION`：明细补产品批号、加工类型、加工单号、工序汇报单号、工序编码/名称、工序辅单位、应检数量、检验返工数量、工废数量、料废数量、生产车间、工作中心、设备、班组、工人、检验方案、不合格原因；判定集合为 合格/返工/让步接收/报废；合格 + 不合格 = 检验数量，填写返工/工废/料废时三者之和必须等于不合格数量；当前不做下游转换，不挂生单入口，审批流对齐其他质量单据。
- 成品报检单 `FINISH_INSPECT`：表头补供应商编码/委外供应商/部门/负责人；明细补 BOM版本号、供应商(库存)、单价/税率/含税单价/金额/税额/含税金额、预完工日、抽检数量/最大不合格数、累计检验/合格/验收退回/让步/报废/入库/已退数量、不合格原因、检验方案。已出检验结果时「合格+不合格=报检数量」；抽检数量不得超过报检数量，最大不合格数不得超过抽检数量（未填抽检数量时按报检数量）。累计质量结果由检验单审批后沿来源链回写，报检单不手工维护累计值。
- 首件报检单 `FIRST_INSPECT`：来源改为工序汇报单；表头补委外供应商/负责人；明细补 BOM版本号、加工单号、工序汇报单号、加工类型、检验方式/抽检比例/抽检数量/最大不合格数、检验要求、生产车间、班组、工人、累计检验/合格/不合格/检验返工数量、不合格原因、检验方案、板号/数值自定义项。首件报检保持单页签，不新增样本页签；报检到检验/入库的流程转换暂不调整。
- 上述字段组合依据：T+ QM10/QM07 抓取的报检字段、[芋道 MES 质检方案](https://doc.iocoder.cn/mes/qc/template/) 的抽检数量/最大不合格数/上下限、[Carbon](https://github.com/crbnos/carbon) 的 FAI/NCR 质量闭环、[苦糖果 MES](https://gitee.com/kutangguo/ktg-mes) 的首检/终检检验类型。
- 质量明细、统计、执行和追溯报表复用业务单据与来源关系，不另存一套可编辑业务数据。菜单、配置、种子和编号登记统一由 `QualityPanelRegistry`、`ReportPanelRegistry`、`PxService` 与 `init.sql` 共同维护。

## 11. PLM 领域落地原则

PLM 不是把 MES 面板改名。`panel_config` 负责页面描述，`form_data` 可承载低风险扩展字段或原型数据；产品身份、修订版、BOM 行、文档版本、基线和变更关系必须进入结构化领域表，并由独立 Service 维护事务与唯一约束。

初始领域边界应按需求逐项确认，候选对象包括 `Item`、`ItemRevision`、`DocumentRevision`、`BomLine`、`Baseline`、`ChangeRequest` 和 `ChangeOrder`。未确认的对象不提前建表。至少遵守：

1. 产品身份与修订版分离；业务引用指向明确修订版，不能只存显示名称。
2. 已发布修订不可原地覆盖；修改产生新修订并保留审计链。
3. BOM 行使用稳定主键和父子修订外键，数量、单位、生效区间及替代关系不可只存 JSON。
4. 文件二进制与元数据分离；数据库保存版本、校验值、存储引用和权限，不保存临时本机路径。
5. 签出、发布、变更执行和基线冻结属于领域动作，通过 `PanelActionHandler` 进入独立事务。
6. ECR/ECO 的状态机、审批角色、影响分析和回滚策略在实现前形成验收条件。
