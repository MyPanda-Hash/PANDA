# 语音悬浮窗（小缔 · 语音）

> 一个 380×600 的独立小窗口，浮在屏幕上随时说话。回答同时以字幕气泡和语音给出，
> 业务数据由后端实时查 MES，还能**把待办和通知派到具体人身上**，
> 并且会**跟踪这些待办的进展**——谁还没开始、卡了多久，到点自动催、催不动升级。
> 派下去的每一件都会**以微信式气泡弹到收件人面前**（门户、群聊、悬浮窗都会弹）。
> 边界：MES 单据只查不改；能写的是 AI 自己的东西（待办、群消息）。

## 1. 怎么打开

| 方式 | 操作 |
|---|---|
| 门户入口（推荐） | 打开 <http://localhost:18091>，左侧导航点「语音助手」 |
| 直接访问 | <http://localhost:18091/pod> |
| 钉在最前 | 窗口右上角「↑」按钮，用 Chrome 的 Document PiP 变成一个无边框、始终置顶的小窗 |

窗口名固定为 `dnx-voice-pod`，重复点入口只会复用同一个窗口，不会开出一堆。

> 麦克风只在 `localhost` 或 HTTPS 下可用；换机器的局域网地址访问需要配 TLS。

## 2. 能做什么

对着窗口说话，例如：

- 「中天客户最近有哪些订单？」→ 查销售订单
- 「SO-20261112-003-1 做到哪一步了？」→ 查生产工单
- 「包装木箱还有多少库存？」→ 查库存
- 「我这周还有什么没做的？」→ 查自己的待办

模型自己判断该查哪张面板，查完把结果念出来，同时把单据列成卡片显示在气泡上方。

还能派活：

- 「让张仓管补一下包装木箱」→ 给张仓管建一条待办，回报「已经派给张仓管了」
- 「通知王销售明天中天来看厂」→ 在你们的共同群聊里发一条 @他 的通知
- 说不清是谁、或者对上好几个人时，**它会把候选人念出来问你**，不会自己挑一个

还能跟进度、催人：

- 「张仓管那个木箱补了没？」→ 「还没开始，已 2 天没动」
- 「催一下张仓管」→ 在群里 @ 他催一次；名下有多条先问催哪一条
- 不用人问：后台每轮巡检会自己催到期的、催够次数还不动就升级给派活的人

**不能做**（刻意锁死）：

- 改任何 MES 单据、审批、删除——工具表里没有任何写业务数据的口子；
- 查询面板限白名单：销售订单 / 生产工单 / 采购订单 / 到货单 / 库存 + 待办；
- 字段限白名单：不回单据正文，只回单号、客户、状态、数量金额这类摘要；
- 一次通话最多派 `MOSS_VOICE_WRITE_LIMIT` 件（默认 5），防止一句话被拆成十条待办。

## 3. 消息气泡（派活通知）

待办一分配下去，收件人那边会像微信消息一样从右下角滑出一张卡片：

```
┌─────────────────────────────────────┐
│ [缔] 小缔 · 待办  来自 管理员   刚刚 │
│ 安排中天客户午餐与伴手礼             │
│ 两位客户，忌口已登记                 │
│                     [知道了] [去处理] │
└─────────────────────────────────────┘
```

- **在哪里弹**：门户（18091）、`/group` 群聊页、`/pod` 语音悬浮窗，三处都有；
- **弹几次**：一件事只弹一次。弹过的 id 记在浏览器本地，刷新也不重弹；
  未读的会在下次打开时补弹；
- **自动收起**：9 秒后滑走，鼠标移上去会暂停倒计时；
- **知道了** → 标记已读；**去处理** → 打开群聊去办事；
- **桌面通知**：页面在后台且已授权时，同时发一条系统通知（和微信桌面端一样）。

实现：`GET /api/notifications` 轮询（8 秒一次，页面隐藏时照常拉、只是不发系统通知），
`POST /api/notifications/read` 标记已读。没有用 WebSocket——少一类断线重连的问题。

**谁会收到**：只有被派活的人自己。管理员不代收别人的提醒。
同一个人、同一件事（`dedupe_key`）在有未读时不会再堆一条。

## 3.0 单据跳转与 MES 悬浮窗

### 点一下就回到单据

待办里只要涉及 MES 单据，抽屉底部会多一块「关联单据」：

```
关联单据（3）
[其他入库单 OTHE-20261112-008        去处理 ↗]
[其他出库单 OTHE-20261112-007        去处理 ↗]
[其他入库单 OTHE-20261112-004        去处理 ↗]
```

点开就是 MES 对应表单页：`/#/panelx/form/OTHER_IN?code=OTHE-20261112-008`，
落地页标题「其他入库单 · 轻MES」，审批通过 / 审批驳回都在。

链接由后端拼：`MES_WATCH_UI_URL` + `/#/panelx/form/<面板>?code=<单号>`。
面板与单号来自 MES 开放接口的返回值，不是从标题里猜的。

### 同类问题排查（2026-11-13）

顺着「顶部不一样」查了一遍外部入口，发现三处同类问题，两处已修：

| # | 问题 | 表现 | 状态 |
|---|---|---|---|
| 1 | `/panelx/form/:面板` 深链不建页签 | 页签栏只剩「我的桌面」，单据没法关 | ✅ 已修 |
| 2 | 单据加载失败后页签残留 | 失效链接会留一张打不开的单据页签 | ✅ 已修（失败时关掉自己） |
| 3 | 链接主机名写死 | 后端按 `MES_WATCH_UI_URL` 拼 `localhost`，人在 `127.0.0.1` 上点过去就是未登录（MES 登录态按源隔离） | ✅ 已修（按当前页面主机名对齐） |
| 4 | 失效链接跳转后多一个「XX-新增」页签 | 只在单号不存在时出现 | ⚠️ 未修，影响小 |
| 5 | `#/print/invoice` 深链无页签 | 打印页，一般新窗口打开 | ⚠️ 已知 |

查过没问题的：

- `#/panelx/list/:面板` 深链——列表页会自己建页签，标题也对；
- `?code=` 对主键字段不同的面板同样有效（生产工单主键是「编号」，实测能定位到单据）；
- 审批待办的分派人——本来就由 MES 的开放接口决定，不会有「派给没权限的人」。

第 3 条的具体做法：群聊页把链接里 `localhost` / `127.0.0.1` 换成当前页面的主机名
（只在两边都是回环地址时替换）；MES 里的待办球直接用 `location.origin`，因为它本来就跑在 MES 里。

### 深链进来为什么「顶部不一样」以及怎么修的

从待办点过来的地址是 `/#/panelx/form/OTHER_IN?code=OTHE-...`，**MES 的页签是在应用内打开时才创建的**
（`tabs.open()` 由列表页/菜单调用），直接命中动态路由不会建页签。结果就是：单据内容占着屏幕，
页签栏却只剩「我的桌面」，顶部看着跟平时不一样，也没法关掉这张单据。

修在 `light-mes/frontend/src/layout/PortalLayout.vue`：路由变化时如果找不到对应菜单项
（外部深链、书签、刷新都属于这种），给 `/panelx/form/<面板>` 补一个页签；
表单加载完会自己把标题改成「面板名-单据号」，所以最终显示和正常打开一致。

### MES 里也有一个待办球

MES 页面右下角常驻一个绿色小球（`7 待办`），点开是「我的待办」：

- 每条待办下列出它关联的单据，点「去处理」直接跳到表单；
- 15 秒轮询一次，切回页面立刻刷新；
- 底部有「在群聊里看待办 ↗」去群聊页做更复杂的操作。

登录态用 MES 现成的 `/api/ai/sso-ticket` 换 AI 会话；换不到就显示「去登录」，
**不假装有数据**。

> 注入方式：`light-mes/frontend/index.html` 里一行 `<script>`，只在 `:4173` / `:5173`
> 页面生效，其它端口自动不启用。`dist/index.html` 也同步加了一份，**重新 build 会覆盖
> dist，但源码里已有，下次构建仍会带上**。

### 审批待办只给有权限的人

审批类待办的分派人不是我们决定的，是 MES 说的：

```
GET /api/open/approvals/pending?approver=admin
→ 只返回 admin 有审批权的面板下的单据
```

所以「3 张单据待你审批」只会落到真正能点「审批通过」的人身上；
删账号、收回权限之后，下一条待办就不会再派给他。
单测 `test_approval_only_targets_the_person_mes_named` 钉住了这条。

原来的侧边栏把整段明细塞进 300px 宽的卡片里，字号 12、行高挤，读不下去。

**详情抽屉**（点任意一行打开）

配色沿用本项目的墨绿主色（`#2f6b58`）与暖白底，只借 antd 的结构、间距与字号阶梯。

## 1.1 最小化为悬浮球

右上角「−」把窗口收成一个球：**点击展开，拖动移动位置**。

形态参考 Ant Design `FloatButton`（悬浮、圆形、主色实心、带投影），
动效遵循设计库的「自然 / 高效 / 克制」：

| 动效 | 时机 | 取值 |
|---|---|---|
| 入场缩放 | 最小化瞬间 | `scale 1.18→1`，200ms，`cubic-bezier(.215,.61,.355,1)` |
| 双层光环 | 待命 | 3.6s 循环，错开 1.8s，扩到 1.55 倍淡出 |
| 光环加速 | 通话中 | 1.8s |
| 声波条 | AI 说话 | 三根竖条错峰跳动，0.9s；此时「缔」淡出让位 |
| 光环转暖色 | AI 说话 | 换成 `--warn`，0.9s |
| 悬停 / 按下 | 鼠标 | 放大 1.05 / 缩到 .96，200ms / 100ms |
| 拖拽中 | 拖动 | **关掉过渡**（跟手优先），光环暂停 |

`prefers-reduced-motion: reduce` 时全部动画关闭。

### 窗口能不能缩小，决定了两种形态

最小化要靠 `window.resizeTo` 把窗口缩到 148×176。这个能力只对
**脚本用 `window.open` 打开的独立窗口**有效：

- **缩得动** → 球居中填满小窗口，拖球即拖窗口；
- **缩不动**（比如把 `/pod` 当标签页打开）→ 窗口保持原样，球**居中**显示，
  下面一行说明「把窗口拖小，球会自动居中填满」，手动拖小后球自动贴合。

> 本机自动化浏览器里 `resizeTo` 被忽略（页面被并到一个大窗口的标签页里），
> 所以「缩成小球」这一路只验证了代码分支与回退形态，**真实弹窗下的缩小未能在此环境实拍**。
> 在 Chrome 里用门户的「语音助手」入口打开的是独立弹窗，属于有效路径。

## 2.0 群聊页的外观与群管理

### 外观切换

右上角「管理员 ▾」下拉里可以切 **浅色 / 深色 / 跟随系统**：

- 选择存在 `localStorage.dnx-theme`，刷新、换页都记住；
- 「跟随系统」不存值，跟着 `prefers-color-scheme` 实时变；
- 主题在 `<head>` 里先定下来再渲染 CSS，避免先白后黑的闪屏；
- 原来的暗色是写死在 `@media (prefers-color-scheme: dark)` 里的，现在改成
  `:root[data-theme="dark"]` 驱动，一份调色板，系统偏好和手动选择共用。

### 解散群聊（解散不删数据）

同一个下拉里，只有**组长或系统管理员**能看到「解散该群聊」。

点它会先弹确认框，写清后果再让你点第二次：

```
解散「AI 调度台」？
群会从列表里消失，成员也看不到它了。聊天记录、附件、待办都会保留，
AI 还会从这段讨论里提炼项目经验，进员工知识库。
                                              [取消] [确认解散]
```

确认后调 `POST /groups/{id}:dissolve`，群被**归档**而不是删除：

| 项 | 解散后 |
|---|---|
| 群本身 | `status=archived`，从「我的项目群」消失 |
| 聊天记录 / 附件 | 全部保留，能重新打开看 |
| 群里的待办 | 保留，状态不变 |
| 成员关系 | 保留 |
| 提炼经验 | 自动跑一次，结果进员工知识库 |

左栏多一栏「已解散（N）」，展开能看到这些群；点进去是只读视图
（输入框隐藏、邀请与整理按钮隐藏），群头有「提炼经验」按钮可以手动补跑。
硬删除 `DELETE /groups/{id}` 仍然保留，但界面不再调用它。

### 解散后自动提炼

解散接口把提炼放到后台任务里跑（要调模型，几秒到几十秒，不能让按钮一直转）：

```
POST /groups/{id}:dissolve
  → 归档 + 审计
  → background: extract_from_groups(group_ids=[id])
  → ProjectExperience 卡片（状态 unverified，等管理员核实）
```

`extract_from_groups` 原来只扫 `status == "active"` 的群，现在支持指定群 ID，
**不看状态**——已解散的群正是最该提炼的：讨论已经结束，素材不会再变。

实测（解散一个真实讨论过的临时群）：

```
解散: 200
解散后仍在列表: 临时-经验提炼验证 / archived
历史消息条数: 4
后台提炼: dissolve distillation cards=1

卡片「木箱加厚至15mm防破损」
  问题：客户反馈上次运输破损三件，要求木箱加厚到15mm。
  做法：将CL005木箱规格改为1200x800x15，由北方机械下周提供样件，验收通过后再批量下单。
  教训：包装规格变更须先做样件验收，通过后再批量执行。
  标签：包装标准 / 供应商样件 / 验收流程
```

### 计数气泡对齐

「待办 7」「我的待办 7」里的数字原来按 inline 基线排，比按钮中心低了 3–4px。
改成 `.pill` 定高 18 + flex 居中，`.tab` 也换成 flex 容器——实测圆心偏差从 3.8px 降到 0。

## 3. 待办归类（同一件事只留一条）

现场问题：对「中天客户来访」这一件事，语音里分几回说了接送车辆、样品清单、
午餐伴手礼、参观路线、接待准备，结果冒出 6 条待办，看着像 6 件事。

现在会算一个**主题键**再决定是新建还是并入：

| 主题键 | 由什么决定 |
|---|---|
| 单号 | 标题里出现 `SO-20261112-003` / `PO-2026-08-0001` 这类单号 → 按单号归类 |
| 主要对象 | 客户 / 供应商 / 厂家（「中天客户」会补全成「中天精工」） |
| 粗类别 | 只有 5 类：事务接待 / 业务交付 / 财务 / 生产 / 质量 |

同一人 + 同一主题键 + 还没完成 + 在 `TODO_MERGE_WINDOW_DAYS`（默认 7 天）内
→ **并进已有那条**，新说的这件事作为一行明细追加进去，不新建。

```
【管理员】核对明天中天客户的接待准备
  会议室、样品、质检报告三样都要齐
  · 确认中天客户来访的产线参观路线（从冲压到装配，绕开正在调试的折弯机）
  · 把中天客户的样品提前摆到会议室（红色样件三套，附质检报告）
  · 安排中天客户午餐与伴手礼（两位客户，忌口已登记）
  · 准备中天客户的样品清单（三套样件）
  · 确认中天客户的接送车辆（上午九点到厂）
```

**刻意不合并**的情况：

- 同一客户但不同性质的事——招待 / 发货 / 回款 分属不同类别，各留一条；
  一句「安排中天客户来访接待」和一句「确认中天订单明天发货」不会并；
- 只提到对象、说不出做什么（「整理一下资料」）→ 不归类，各留一条；
- 超过时间窗、或已经完成的，不会并进去。

**已知取舍**：靠规则不靠模型。规则可测、可解释，但遇到很绕的说法会归不上，
那时宁可分开也不乱并。归类只看标题，不看明细——明细里混着派发人和建议，
拿来判断会把「管理员」「质检报告」当成主题。

存量整理：

```bash
cd doc-nexus-ai/backend
.venv/bin/python scripts/merge_duplicate_todos.py           # 预览
.venv/bin/python scripts/merge_duplicate_todos.py --apply   # 执行
```

被并掉的那条只是置为「已取消」，正文全部搬进保留那条的明细，不删数据。

## 3. 待办状态回流

「状态」由人在群里点（接受 / 开始 / 完成），AI 只做三件事：算、催、升级。

### 状态怎么算

| 状态 | 判定 | 显示 |
|---|---|---|
| 刚派下去 | pending 且还没到阈值 | 「刚派下去」 |
| 还没开始 | pending 超过 `TODO_IDLE_NUDGE_HOURS`（默认 24h）没动 | 「还没开始，已 2 天没动」 |
| 进行中但停住了 | doing 超过 `TODO_STUCK_HOURS`（默认 48h）没动 | 「进行中但停住了」 |
| 已超期 | `due_at` 已过且未完成 | 「已超期 1 天」 |
| 已完成 / 已取消 | 终态，不再跟进 | — |

「多久没动」只认**人的动作**（`last_action_at`）。AI 自己催一次不会把计时清零——
这是实测踩到的坑：最初拿 `updated_at` 当基准，催完立刻变回「刚派下去」。

### 催与升级

- **自动催**：每轮巡检（`MES_WATCH_INTERVAL_SECONDS`，默认 60s）扫一遍未完成待办，
  命中「还没开始 / 停住了 / 超期」就在群里 @ 当事人催一次；
- **冷却**：同一件事 `TODO_NUDGE_COOLDOWN_HOURS`（默认 12h）内只催一次，不刷屏；
- **升级**：催满 `TODO_MAX_NUDGES`（默认 3）次还没动，转给派活的人（没有就找组长）；
- **发不出去就说没发**：没有可用通知群时催办直接返回失败，不假装催到了。

### 语音能问什么

```text
「张仓管那个木箱补了没？」   → 还没开始，已 2 天没动
「大家手上还有多少没做完？」 → 未完成的待办 N 条，其中 M 条卡住了（管理员）
「催一下赵车间那个试模结果的」→ 已经在群里催了赵车间一次
「催一下张仓管」             → 他名下有好几条，问清催哪一条（不挨个催）
```

## 3. 它和「AI 主动监控」的分工

这是最容易误会的地方：

| 能力 | 归谁 |
|---|---|
| 人和 AI 实时对话、边听边说、被打断 | **本模块**（MOSS-Live） |
| 定时扫 MES、发现异常、生成待办、发通知 | `assistant_watch`（与语音无关） |

「全天候」指的是**窗口一直在、随时能开口**，不是「它会自己盯着系统」。
巡查逻辑仍然是后台定时任务，两者互不依赖：关掉语音窗口，主动监控照常跑。

## 4. 架构

```
浏览器（/pod 页面）
   │  ws://localhost:18091/api/assistant/voice/ws
   │  ↑ 同源，Cookie 鉴权；上行裸 PCM16 16k，下行事件 + PCM 音频
   ▼
serve-ai-web.mjs（18091）
   │  upgrade 隧道原样转发（浏览器 WS 设不了 Authorization 头）
   ▼
FastAPI /api/assistant/voice/ws（8000）
   │  持密钥、下发人设与工具、在服务端执行只读查询
   ▼
wss://api.mosi.cn/v1/realtime?model=moss-live-1.0
```

后端中继做四件事，缺一不可：

1. **密钥不出后端**：API Key 只在服务端拼接 `Authorization` 头；
2. **会话配置只能服务端下发**：上游对 `session.update` 字段校验极严，多一个键就断连；
3. **业务工具在服务端跑**：MES 凭据不进浏览器，前端只收到结果；
4. **限流与互斥**：同一用户同时只允许一条语音连接，单次会话有时长上限。

## 5. 协议要点（本机实测）

| 项 | 结论 |
|---|---|
| 握手 | `GET wss://api.mosi.cn/v1/realtime?model=moss-live-1.0&user=<id>` + `Authorization: Bearer`；无 key 返回 403 `missing bearer api key` |
| 会话流程 | `attach_session` → `session_attached` → `session.update`（人设/指令/工具）→ `session.updated`（检查 `data.error`）→ `media.configure` → `media.configured` → 送音频 |
| 音频格式 | 上行 PCM16 16 kHz 单声道，20 ms 一帧 320 采样（640 字节）；下行同格式（本模块把 `output_audio` 固定为 16 k） |
| 判停 | 语音结束后必须**继续送静音**，上游才会判定这一轮说完；只送人声不送尾巴会一直等 |
| 播放回执 | 用 `playback: "server"`，服务端按实时速度代为确认，前端只排队播放，弱网下不会因回执丢失卡住 |
| 工具调用 | `response.function_call_arguments.done` → 执行 → `conversation.item.create`（`function_call_output`）→ `response.create` |
| 打断 | 模型自己听音频判断，前端收到 `response.audio.stop` 时清空播放队列 |
| 音色 | 只能发 `change_voice`，`session.update` 里带 voice 相关字段会被 `invalid_public_request` 断开 |
| 计费 | `moss-live-1.0` 目前限时免费（0 积分），正式计费后按**连接时长** |
| 网络 | `api.mosi.cn` 本机直连可达（约 130 ms），不需要代理；但本机有 SOCKS 环境变量，`websockets.connect` 必须显式 `proxy=None` |

## 6. 配置

根目录 `.env.local`：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MOSS_API_KEY` | 空 | **必填**。留空时语音入口提示「未配置 MOSS_API_KEY」，其他功能不受影响 |
| `MOSS_REALTIME_MODEL` | `moss-live-1.0` | 上游模型 ID |
| `MOSS_REALTIME_URL` | `wss://api.mosi.cn/v1/realtime` | 必须是 `wss://` |
| `MOSS_VOICE_ID` | 暖暖 | TTS 音色 ID，取自 `/v1/audio/voices` |
| `MOSS_VOICE_PERSONA` | `小缔` | 人设名 |
| `MOSS_VOICE_MAX_SECONDS` | `900` | 单次会话上限（30–3600）。到点自动挂断 |
| `MOSS_VOICE_ENABLED` | `1` | 置 0 关闭整条语音通道 |
| `MOSS_VOICE_WRITE_ENABLED` | `1` | 置 0 后只剩查询，不能派待办/发通知（工具表里直接不出现） |
| `MOSS_VOICE_WRITE_LIMIT` | `5` | 单次通话最多派几件（0–50） |
| `MES_WATCH_UI_URL` | `http://localhost:4173` | 拼单据跳转链接用的 MES 前端地址 |
| `DOC_NEXUS_FRONTEND_ORIGIN` | 见 `.env` | CORS 白名单，MES 悬浮窗要能跨端口调 AI 接口 |
| `TODO_MERGE_WINDOW_DAYS` | `7` | 同一件事多久内并成一条（超过就新建） |
| `TODO_FOLLOWUP_ENABLED` | `1` | 置 0 关闭自动催办（查询与手动催办仍可用） |
| `TODO_IDLE_NUDGE_HOURS` | `24` | 多久没动算「还没开始」 |
| `TODO_STUCK_HOURS` | `48` | 「进行中」多久没动算卡住 |
| `TODO_NUDGE_COOLDOWN_HOURS` | `12` | 同一件事两次催办的最小间隔 |
| `TODO_MAX_NUDGES` | `3` | 催几次之后升级 |

改完重启 AI 后端（`bash start-local.sh` 或单独重启 `app.server`）。

## 7. 安全与数据

- **读写分离**：6 个查询工具声明 `read_only: true` + `async_query`；只有
  `assign_todo` / `send_notice` 是 `async_effect`，它们只写待办表和群消息表，**不碰 MES**；
- **派活可见性**：普通员工只能给「自己 + 同群的人」派活，管理员才看得到所有人——
  防止随便给不认识的同事派单；
- **不猜人**：姓名/岗位解析不出来或有歧义时返回失败与候选名单，由模型开口问；
- **留痕**：待人记录 `created_by_user_id`，明细里带「语音派发，来自「某某」」；
- **跟进不改人做的事**：AI 只写 `nudged_at`/`nudge_count`/`escalated_at`，
  不改待办状态——「完成」只能由人来点；
- **白名单**：面板、字段都走 `group_tools.QUERYABLE_PANELS` / `SAFE_FIELDS`，与群助手同一套边界；
- **前端指令白名单**：浏览器只能发 `ping` / `mic_state` / `video.state`，其余丢弃，
  前端无法改写会话配置；
- **鉴权**：WS 优先读同源 `doc_nexus_access` Cookie，也接受 `?token=`（复用现有 JWT）；
- **已知缺口**：语音是整段上行到上游的，**没法像文本那样逐字脱敏**。指令里禁止它念
  客户全名、手机号这类标识，但不能当作硬保障。介意就别在通话里说敏感信息。

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 语音原文直传上游 | 见上，无法逐字脱敏 |
| 单轮工具链可能很长 | 模型会连着查两三张面板，卡片会堆叠；已支持一卡一次调用 |
| 不主动开口 | 配置完一直送静音它也不说话，必须用户先讲 |
| 判停靠静音 | 通话中前端持续送 20 ms 静音帧，麦克风被系统抢占时会表现为「它没反应」 |
| 置顶依赖 Chrome | Document PiP 只有 Chrome/Edge 支持，Safari 不支持 |
| 只在 localhost 可用麦克风 | 局域网访问要配 HTTPS |

## 10. 排障

| 现象 | 排查 |
|---|---|
| 点登录门口 | AI 门户没登录；`/pod` 与门户同源，门户登录一次即可 |
| 「未配置 MOSS_API_KEY」 | `.env.local` 没写或后端没重启 |
| 「你已经有一个语音窗口在通话中」 | 另一个窗口还连着；断开后 2 秒内会释放，或等旧连接被判定断开 |
| 点按钮没反应、几秒后失败 | 看 `/tmp/doc-nexus.log` 有没有 `moss_voice.handshake_failed` |
| 有字幕没声音 | 检查系统输出设备；下行是 16 kHz PCM16，浏览器会自动适配 |
| 说到一半它不说话 | 上游判停没触发，继续说一句或稍等；持续复现查 `input.speech.stopped` 是否到达 |
| 「没找到这个人」 | 语音公只能给同群的人派活；把那个人拉进你的群，或换管理员账号 |
| 「没有共同的群聊」 | 通知发不到对方那里，改口说「给他派个待办」 |
| 卡上说「匿名待办已存在」 | 同一个人名下已有同名未完成待办，不会重复建 |
| 它说「刚催过」 | 冷却中（默认 12h），要立刻再催得等冷却结束或调小 `TODO_NUDGE_COOLDOWN_HOURS` |
| 状态一直是「刚派下去」 | 人没动过；超过 24h 才会变「还没开始」，阈值可调 |
| 群里没收到催办 | 通知群没配（`MES_WATCH_GROUP_NAME`），日志里会有 `todo_followup.no_feed_group` |
| 没弹气泡 | 看 `/api/notifications` 有没有未读；弹过的不会重弹（清 `localStorage` 的 `dnx_notified_ids` 可强制重弹） |
| 只有桌面通知没有页面气泡 | 页面在后台；回到前台会自动补弹 |
