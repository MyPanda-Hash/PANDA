# 语音助手 × AI 助手融合

> 目标：语音不只是聊天，而是「像真实助理一样」按**你自己的权限**去 MES 取数、分析、汇报、派活。
> 代码：`backend/app/services/moss_voice.py`、`mes_user_client.py`、`production_briefing.py`、`group_tools.py`。

## 1. 原来的问题

语音助手与群助手都用 `MES_WATCH_USERNAME` 那个账号查 MES —— 那是**管理员视角**。
普通仓管问一句「库存多少」，AI 会拿管理员的结果回答：既不安全，也不符合「你能看什么就答什么」。

## 2. 现在的链路

```text
用户说话
   ↓ 实时语音（MOSS）转写 + 工具调用决策
   ↓ 工具执行（服务端，只读）
mes_user_client.client_for_user(user_id)      ← 用 mes_user_bindings 里绑定的 MES 账号登录
   ↓ 权限门禁：can_query(panel) / can_approve(panel)
   ↓ 通过 → 以该用户身份查 MES（MES 自己也会再判一次）
   ↓ 不通过 → 明确说「你的 MES 账号没有 X 的查看权限」，不降级成管理员
回答 / 汇报 / 派活
```

判定权限的数据来源就是 MES 登录返回的 `visiblePanels` / `approvePanels` / `isAdmin`，
缓存 5 分钟（`mes_user_client.access_of`）；没绑定 MES 的人得到的是「先去 MES 点 AI 数字员工完成绑定」。

## 3. 新增：生产概况汇报（`production_briefing`）

一句话回答「今天生产怎么样、有什么异常」。组合口径：

| 板块 | 面板 | 口径 |
|---|---|---|
| 加工单 | `MANU_ORDER` | 总数、在制数（状态非完工） |
| 超期 | `MANU_ORDER` | 预完工日 < 今天且未完工 → 列前 3 张 |
| 今日完工 | `FINISH_IN` | 单据日期 = 今天 |
| 今日报工 | `PROCESS_REPORT` | 汇报日期 = 今天 |
| 低库存 | `STOCK_STATUS` | 现存量 < 500 → 列前 3 项 |
| 待审批 | `SO_ORDER` | 状态 = 审批中 |

**按权限逐块取数**：没有权限的板块不查、不静默吞掉，而是在汇报里点名「XX 你没有权限，这部分跳过了」。

实测（同一句话，两种账号）：

```text
admin        → 生产概况：加工单 7 张，在制 1 张；今日产成品入库 0 单；今日工序汇报 0 单；
                低于 500 的物料 9 项；销售订单审批中 0 张。
受限销售账号  → 生产概况：销售订单审批中 0 张。生产加工单、产成品入库单、工序汇报单、
                库存状况表 你没有权限，这部分跳过了。
受限账号查库存 → 你的 MES 账号没有「STOCK_STATUS」的查看权限，这条我不能替你看
```

## 4. 语音能调的工具（全部只读，写操作另有白名单与次数上限）

| 工具 | 作用 | 权限 |
|---|---|---|
| `query_sales_orders` / `query_work_orders` / `query_purchase_orders` / `query_arrivals` / `query_inventory` | 面板查询 | 按该用户的 `visiblePanels` |
| `trace_doc` | 单据走到哪、卡在哪、下一步 | 开放业务接口（只读） |
| `doc_detail` | 单据表头与明细 | 同上 |
| `production_briefing` | 生产概况 / 异常汇报 | 逐块按权限 |
| `list_my_todos` / `query_todo_status` | 我的待办 / 某人的进展 | 按 `approvePanels` |
| `assign_todo` / `send_notice` / `nudge_todo` | 派活、发通知、催办 | 写操作白名单 + 每次通话次数上限 |

## 5. 边界

- 语音**不改单据**：查询全是只读；派活只生成待办/通知，不动业务数据。
- 权限只收紧不放大：绑定缺失 → 报错让人去绑定，不退回管理员视角。
- 取数失败（MES 不可达）→ 汇报里标「查询失败」，不当成「没有数据」。

## 6. 主动汇报（2026-11-14 升级）

从「你问我答」升级到「到点主动说」。三层：

| 层 | 触发 | 内容 | 投递 |
|---|---|---|---|
| **早间汇报** | 每天第一轮扫描（`MES_MORNING_PLAN_ENABLED`） | 生产概况（权限内）+ 个人今日优先处理的 N 件事 | 站内通知（每人一条，按天去重）+ 群里一条总览 |
| **异常事件** | 每轮扫描（默认 120s） | 超期工单、低库存、待审批积压、到货未检、停滞未报工… | 派待办给具体的人 + 追催/升级 |
| **随时查看** | 打开语音悬浮窗 / 调接口 | 当前账号的生产概况 | 悬浮窗顶部卡片（`GET /api/assistant/briefing`） |

**权限贯穿三层**：早间汇报用 `production_briefing.for_user(user_id)`，也就是用这个人自己的
MES 账号取数——管理员看到 7 张工单 9 项低库存，受限销售看到的只有「销售订单审批中 0 张」，
其余板块明确标注「无权限，跳过」。

实测（同一次 `post_morning_plan` 推送）：

```text
管理员    → 早间汇报：2 件待处理
            生产概况：加工单 7 张，在制 1 张；今日产成品入库 0 单；今日工序汇报 0 单；
            低于 500 的物料 9 项；销售订单审批中 0 张。
张仓管    → 早间汇报：3 件待处理（未绑定 MES 时不再插入「请先绑定」的提示，
            只推他自己的待办，避免每条前面挂一句绑定广告）
```

## 7. 语音悬浮窗的主动展示

打开 `/pod` 时自动拉 `GET /api/assistant/briefing`，在顶部显示一张卡片：

- 一句话概况 + 最多 4 条要点（低库存/超期单据，「低库存」用暖色标签）
- 有权限跳过的板块会写「无权限未报：X、Y」，不让人误以为数据是全的
- 右上「刷新」实时重算；卡片不自动朗读，避免打断正在进行的通话

接口 `GET /api/assistant/briefing/notifications?limit=5` 还能取回最近几条主动推送，
供「今早跟我说了什么」这类问法使用。

## 8. 通话开场播报（2026-11-14）

接通语音后不再等用户先开口：先念一句今天的生产概况，再停下来等指令。

**实现路径**（不额外走 TTS，复用通话本身的声音）：

```text
建立 WS → attach_session → session.update
    └─ instructions 里追加【开场播报】段：一到两句、别念编号、别逐条重复数字
       + 该用户权限内的概况文本（production_briefing.for_user）
→ media.configured（音频通道就绪）
→ response.create（空 response，让模型主动说第一轮）
```

要点：

| 项 | 处理 |
|---|---|
| 取数时机 | 握手时在线程里取，超时 12s；取不到/未绑定 → 不播，安静开场 |
| 长度 | `moss_voice_briefing_chars`（默认 220），按分句截断，不在数字中间切 |
| 开关 | `MOSS_VOICE_BRIEFING_ENABLED`（默认开） |
| 失败兜底 | `response.create` 不被支持时只记日志，退化成「等用户先说话」，不断连 |
| 顺序 | 必须在 `media.configured` **之后**触发，否则第一句没有可播放声道 |

实测（生成侧）：`opening_briefing(admin)` →
`生产概况：加工单 7 张，在制 1 张；今日产成品入库 0 单；今日工序汇报 0 单；低于 500 的物料 9 项；销售订单审批中 0 张。`
未绑定 MES 的用户返回空串（不播「请先绑定」这类系统提示，那不像人说话）。

测试：`tests/test_voice_opening.py` 5 例（instructions 带/不带开场、开关关闭、取数失败、按分句截断）。

## 9. 订阅式盯单（2026-11-14）

「盯着 PO-2026-08-0001，到货就告诉我」——从被动查询变成**持续关注**。

### 怎么用

语音说三种话，对应三个工具：

| 说法 | 工具 | 行为 |
|---|---|---|
| 「盯着 SO-2026-08-0004，生产工单出了告诉我」 | `watch_doc(doc_no, step='生产工单')` | 建订阅，只在该环节出单时报 |
| 「这单一有变化就通知我」 | `watch_doc(doc_no)` | 任何环节推进都报 |
| 「盯着它，卡住了告诉我」 | `watch_doc(doc_no, condition='卡点')` | 出现卡点时报 |
| 「我都在盯什么」 | `list_watches()` | 列出活跃订阅 |
| 「别盯了」 | `cancel_watch(doc_no)` | 取消 |

### 判定逻辑

只依赖 MES 的流程追踪（`trace`），不改任何单据：

```text
建订阅时：基线快照 = {已完成数, 环节数, 当前环节, 卡点, 各环节{名称,面板,单号,状态}}
每轮扫描：再取一次 trace → 比较
   target_kw 有值 → 该环节「没单号 → 有单号」才算命中
   condition=stalled → 卡点单号从无到有
   其他             → 已完成数增加，或环节数增加
命中 → 站内通知「盯单提醒：<单号>」+ 更新基线
```

### 几条刻意的边界

| 情况 | 处理 |
|---|---|
| 单号查不到流程 | 拒绝建订阅：「没查到 X 的流程，确认一下单号」 |
| **流程已经全部走完** | 拒绝：「X 的流程已经全部走完，不用盯了」 |
| 没有该面板权限 | 拒绝并说明（复用 `mes_user_client.can_query`），不给自己开管理员视角 |
| 同一信号重复出现 | `last_signal` 去重，同一条只报一次 |
| 订阅过期 | 默认 7 天（1–30 可调），到期自动置 done |
| MES 不可达 | 单条失败只记日志，不影响其他订阅 |

### 实测（真链路：真实 MES 单据推进 + 真实扫描）

```text
订阅  → 好，盯 SO-2026-08-0004：生产工单环节出单。有变化我第一时间告诉你，不用再问。
基线  → 已完成 1/4，当前步骤只有「销售订单」
扫描  → checked: 1, hit: 1
通知  → 盯单提醒：SO-2026-08-0004
        生产工单环节已生成单据 MO-TEST-0001（生产工单）
再扫  → hit: 0（同一信号不重复报）
取消  → 好，SO-2026-08-0004 不再盯了。
接口  → GET /api/assistant/watches 200；DELETE 不存在的单号 404
```

### 落地位置

- 后台：每轮 MES 扫描之后跑一次 `doc_watch.scan`（`background_workers._mes_watch_loop`）
- 通知走站内通知，MES 顶部铃铛 / 待办里能看到
- 测试：`tests/test_doc_watch.py` 6 例（推进、无变化、只盯某环节、卡点、查不到单号、已走完）


## 10. 真链路验收（2026-11-14，全程真实数据）

前面第 9 节第一次验收用的是构造的 trace。这次按用户要求走**真实业务动作**，验证整条链路：

```text
1) 建订阅      watch_doc(SO-2026-08-0004-1)            → 基线 3 环节
2) 真实推进    POST /api/px/firstInspectByBatch        → 生成首件报检单 SJ-20261114-001
3) 真实扫描    doc_watch.scan（不注入假数据）           → hit=1
4) 通知        盯单提醒：SO-2026-08-0004-1
               首件报检单环节已生成单据 SJ-20261114-001
5) 后台链路    新建订阅 → 真实排产（SO-20261114-001 → 加工单 SO-20261114-001-1）
               → 等后台 worker 一轮
6) worker 日志 14:17:45 doc watches signalled {'checked': 3, 'hit': 1, 'expired': 0, 'failed': 0}
   通知        盯单提醒：SO-20261114-001 | 流程推进：已完成 3/12 环节，当前 SO-20261114-001-1
```

真链路暴露并修掉的 4 个问题（都是模拟数据测不出来的）：

| 问题 | 现象 | 修法 |
|---|---|---|
| **只看完成数会漏推进** | 首件报检单刚建出来是草稿，`已完成数` 不变 → 不报 | 新增「下游环节冒出带单号的步骤」判据，优先级最高 |
| **口语与面板名不一致** | 用户说「生产工单」，MES 叫「生产加工单」；说「报工」对应「工序汇报」 | 别名表 + 相似度兜底（≥0.6），解析出的真实环节名存库 |
| **还没走到那一步的订阅** | 环节不存在时会建一个永远不会触发的哑巴订阅 | 降级成「有推进就报」，并在回复里说明当前有哪些环节 |
| **整条流程已走完** | 对已完成的单建订阅毫无意义 | 建订阅时直接拒绝：「流程已经全部走完，不用盯了」 |

另有 `expires_at` 时区比较崩溃（naive vs aware）→ 统一 `as_utc` 后修复。

### 验收留下的痕迹（如实说明）

- 删除成功：`SJ-20261114-001`（首件报检单，草稿态）
- 仍保留：`SO-20261114-001`、`SO-20261114-001-1`、`SO-2026-08-0004-1` 均为 **已中止** 状态

MES 的策略是「只有草稿能删」，已审核单据中止后作为记录保留，所以这三张留在库里。它们是验证材料，
如果要清掉需要在数据库层面处理（不走业务接口）。


## 11. 群聊 AI 助手也支持订阅（2026-11-14）

语音能订阅，群里说话同样能订阅，两边共用同一张 `doc_watches` 表和同一套权限校验。

### 接入方式

群助手不是 function calling，而是「一次返回整段 JSON」的分析协议，所以订阅通过两个新字段表达：

```json
{"watches":[{"doc_no":"SO-2026-08-0004","step":"","note":"跟交期"}],
 "unwatch":["PO-2026-08-0001"]}
```

`analyze_group` 拿到解析结果后：

1. **谁说的谁盯**：订阅落在最后说话的人名下（`focus_sender` 解析成成员），解析不到才退回群主——不替别人建订阅；
2. 走 `doc_watch.create_for_user`（追踪 → 面板权限校验 → 建订阅），和语音完全相同的一条路；
3. 结果写进 AI 回复正文：成功写「已盯 XX：有推进，有变化我会在这里说」，失败写原因（单号不存在 / 没权限 / 流程已走完），**不假装盯上了**；
4. 订阅本身只读，不改 MES 单据。

### 实测（真实群聊 + 真实模型）

```text
群里发   「帮我盯着 SO-2026-08-0004，有推进马上告诉我」
AI 回复  SO-2026-08-0004 已经盯上了，出库、报工、入库任一环节有推进我第一时间报你。
         眼下卡点是 SO-2026-08-0004-1 生产加工单处于中止状态…
         已盯 SO-2026-08-0004：有推进，有变化我会在这里说
落库     doc_watches: SO-2026-08-0004 / user=管理员 / condition=progress
附带     模型还把它整理成了一条待办「恢复或重开生产加工单 SO-2026-08-0004-1」
```

顺带发现了真实问题：单号所在链路走不动时，模型会把「卡点」一起说出来——这正是订阅 + 分析该有的样子。

### 未接的一个入口

**对话页（`/chat`）** 用的是 pi runtime，它的工具 schema 定义在 `pi_runtime/extensions/nexus_capability.ts`，
而本机 `/opt/pi-extensions` 不存在（该 runtime 未挂载），所以那边既改不了也验不了。
要接的话需要：`nexus_mes_watch_doc` 等三个工具（TS schema）+ Python 侧 `MES_CAPABILITY_TOOLS` 处理器，
并在有 pi runtime 的环境里验收。这次没有动它，避免交付一个没跑过的东西。
