## 0. 结论先说

迁移是**中等规模、可控**，不是"换个驱动"：

| 维度 | 实测量 | 结论 |
|---|---|---|
| 代码里的裸 SQL | 14 条 `JdbcTemplate` + 1 条 `@Select` + 12 处 `.last("LIMIT n")` | 小；仅 2 处 upsert 需改写 |
| MySQL 专有语法 | `ON DUPLICATE KEY UPDATE` 2 处（Java）+ 全部种子 SQL；`AUTO_INCREMENT`、`TINYINT`、`ENGINE=`、`ON UPDATE CURRENT_TIMESTAMP`、`SET @var` + `JSON_SET` 一段 | 集中在 DDL 与种子数据 |
| 表 / 列 / 行 | 26 / 411 / ≈2,000 | 数据量小，可整库搬，不需要停机窗口协调 |
| 运维脚本 | `start-local.sh`（docker 启动 MySQL）、`DbBackupService`（mysqldump）、`deploy-*.ps1|sh`（apt 装 MySQL） | 必须改，且是本方案的主要工作量 |
| 文档 / 前端文案 | 13 个 md、4 处前端字符串 | 顺带改 |
| 测试 | 711 条单测，**0 条 `@SpringBootTest`** | 单测不受影响；缺的是"真连 PG"的集成验证，需要补 |

**关键发现（决定策略）**：`init.sql` 只有 19 张表，运行库有 26 张 —— `accounting_account`、`accounting_entry`、`finance_voucher`、`finance_write_off`、`invoice_file`、`sys_backup_log`、`sys_usage_log` 这 7 张由 `migrate_*.sql`（18 个文件）和 `SchemaInit` 在运行时创建/改列。**所以 DDL 的权威源是运行库，不是 `init.sql`**：必须从 `information_schema` 生成 PG 建表语句，不能手工翻 24 个 SQL 文件。

## 2. 目标形态

| 项 | 取值 | 理由 |
|---|---|---|
| 版本 | PostgreSQL **16** | 稳定、Docker 官方镜像成熟；17 无必要新特性 |
| 容器 | `light-mes-pg`，镜像 `postgres:16`，宿主 `127.0.0.1:5432`（本机 5432 空闲，实测 closed） | 与现有 `light-mes-db` 并存，便于回滚 |
| 库 | `light_mes`，schema `public` | 沿用库名，减少配置改动 |
| 编码/排序 | `--encoding=UTF8 --locale-provider=icu --icu-locale=zh-CN` | 中文 ORDER BY 与 MySQL `utf8mb4_general_ci` 观感接近；不要用 `C`（中文按字节排） |
| 标识符 | 全部小写 snake_case（现有列名已全部小写，无一命中 PG 保留字） | 免引号，MyBatis 下划线转驼峰不变 |
| 主键 | `bigint generated by default as identity` | 替代 `AUTO_INCREMENT`；`id` 必须是表的第一列（现有 26 表全部满足） |
| 时间 | `timestamp(0)`（秒精度）+ 应用写入 | 与 MySQL `DATETIME` 行为一致，避免 `LocalDateTime.equals` 因微秒翻转 |
| 标志位 | `TINYINT` + Java `Integer` → `smallint`；Java `Boolean` → `boolean` | 见 §4 分类 |
| JSON | `form_data.data` / `detail_data` / `panel_config.config` 仍是 `text` | 不改 Java 解析路径；`jsonb` 收益低、风险高 |

## 3. 类型映射表

| MySQL | PostgreSQL | 备注 |
|---|---|---|
| `BIGINT PRIMARY KEY AUTO_INCREMENT` | `bigint generated by default as identity primary key` | 建表后补 `setval` |
| `INT` | `integer` | |
| `TINYINT`（Java `Integer`） | `smallint` | 29 列里只 5 列是 `Boolean`（见 §4） |
| `TINYINT`（Java `Boolean`） | `boolean` | `stock_balance.ext_flag1..5` |
| `VARCHAR(n)` | `varchar(n)` | PG 按字符计长，中文与 MySQL 一致 |
| `TEXT` | `text` | 顺带解除 64KB 上限 |
| `DECIMAL(p,s)` | `numeric(p,s)` | |
| `DATETIME` | `timestamp(0)` | |
| `DATE` | `date` | |
| `DEFAULT CURRENT_TIMESTAMP` | `DEFAULT now()` | |
| `ON UPDATE CURRENT_TIMESTAMP`（5 列） | 触发器 `trg_touch_<table>` 或应用层补写 | 代码里已有 61 处 `setUpdateTime`，但覆盖不全 → **统一用触发器**，避免逐处补 |
| `UNIQUE KEY uk_x (a,b)` | `CONSTRAINT uk_x UNIQUE (a,b)` | |
| `KEY idx_x (a)` | `CREATE INDEX idx_x ON t(a)` | 共 13 个 |
| `COMMENT '...'` | `COMMENT ON TABLE/COLUMN` | 278 处，脚本生成，不手工写 |

## 4. 标志位列分类（必须先定，否则运行期报类型错）

`TINYINT` 共 36 列（含 migrate 加的）。判定依据是实体字段类型：

- **Java `Integer` → `smallint`**：`sys_user.enabled`（`SysUser.java:17`）、`sys_role.is_admin`（`SysRole.java:14`）、`sys_role_panel.can_approve`（`SysRolePanel.java:15`）、`manu_order.status`（`ManuOrder.java:31`）、`px_column_pref.visible`、`px_custom_field.in_grid/is_required`、`accounting_account.enabled`、`sys_locale.enabled`
- **Java `Boolean` → `boolean`**：`stock_balance.ext_flag1..5`（`StockBalance.java:56-60`）、`form_data.current_version`（`FormData.java:30`）
- 其余 `ext_flag*`（`manu_order`、`manu_order_item`、`wms_task`、`invoice_file`）实体未映射 → 按 `smallint` 建，将来映射再加

> 坑：若把 `stock_balance.ext_flag1` 建成 `smallint`，MyBatis 会发 `boolean` 参数，PG 报 `column ext_flag1 is of type smallint but expression is of type boolean`。

## 5. 语法改写清单（逐条）

1. **库创建**：`CREATE DATABASE ... CHARACTER SET utf8mb4` + `USE light_mes` → `CREATE DATABASE light_mes ENCODING 'UTF8'`；`USE` 不存在，改 `psql -d light_mes`
2. **upsert**：`ON DUPLICATE KEY UPDATE c = VALUES(c)` → `ON CONFLICT (冲突列) DO UPDATE SET c = EXCLUDED.c`
   - `PxService.java:981` 冲突列 `(panel_code, owner, col_name)`
   - `TranslationService.java:215` 冲突列 `(scope, ref_key, locale)`
   - 种子 SQL / `init_full.sql` / `build-deploy-sql.mjs` 里的 `panel_config` upsert → 冲突列 `(panel_code)`
3. **会话变量 + JSON 手术**（`init.sql:1018-1090`）：`SET @tab_idx`、`JSON_SET(@cfg, path, ...)`、`CAST(@sc AS JSON)`。PG 需 `jsonb_set` 且不能跨语句用 `@var`。**该段是历史上"已执行过的补丁"**，推荐直接删除（改成一次性脚本留档），不要翻译成 `DO $$ ... $$`
4. **`NOW()`**：兼容，保留
5. **`LIMIT n`**：兼容，12 处 `.last("LIMIT n")` 不动
6. **`CREATE TABLE ... AS SELECT`**（backup 表）：兼容，保留
7. **`LIKE` 大小写敏感**：MySQL ci → PG cs。仅 3 处（`SysUsageLogController.java:35`、`ManuOrderService.java:34-35`），中文场景影响小；要保语义改 `ILIKE`（`QueryWrapper` 无对应方法，用 `.apply("col ilike {0}", v)`）
8. **唯一性语义**：MySQL ci 下 `'abc'` 与 `'ABC'` 冲突，PG 视为两个值 → 迁移前用 SQL 确认无大小写重复（`sys_user.user_name`、`panel_config.panel_code`、`form_data.form_no`）
9. **空串/非法值**：MySQL 宽松写入的空串、`0000-00-00`、超长字符串，PG 会拒绝 → 迁移 `COPY` 阶段会直接报错，属提前暴露，不要 `--skip` 绕过
10. **自增回填**：`COPY` 写入显式 id 后必须 `setval(pg_get_serial_sequence('t','id'), COALESCE(MAX(id),1))`，否则下一次 insert 撞主键

## 8.5 回滚窗口的真实语义

切回 MySQL 只是「能立刻恢复服务」，**不会自动回灌切到 PostgreSQL 之后新产生的数据**：迁移完成后所有写入都进 PostgreSQL，MySQL 里停留在 2026-11-13 的快照。因此：

- PG 不可用且需要立刻恢复业务 → 按 §8 切回 MySQL，接受丢失切库后写入，之后人工补录。
- PG 只是慢/有问题但仍可读 → 先用 `pg_dump` 留档再评估，不要直接切回。
- 2026-11-27 之后：删除 `db/*.sql`、移除 `pom.xml` 的 MySQL 驱动与 `DbBackupService` 的 MySQL 分支，回滚能力正式结束。
