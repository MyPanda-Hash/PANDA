# 轻 MES 文档编写规范

| 属性 | 内容 |
|---|---|
| 文档类型 | 开发规范 |
| 适用场景 | 全部场景 |
| 维护状态 | 生效 |
| 最后整理 | 2026-08-24 |
| 文档导航 | [文档中心](README.md) |

## 1. 编码与字体

- 文件编码统一使用 UTF-8，不写 BOM，不允许出现 Unicode 替换字符 `U+FFFD`。
- Markdown 不内嵌 `<font>`、`style` 或 `font-family`，由渲染器统一控制字体。
- VS Code 预览统一加载 [`assets/markdown.css`](assets/markdown.css)。
- 正文字体栈：`Segoe UI`、`Microsoft YaHei`、`PingFang SC`、`Noto Sans CJK SC`、sans-serif。
- 代码字体栈：`Cascadia Code`、`Consolas`、`SFMono-Regular`、monospace。

## 2. 文档头部

每份新文档只能有一个一级标题。规范、设计和日志在标题下使用统一元信息表：

```markdown
# 文档标题

| 属性 | 内容 |
|---|---|
| 文档类型 | 开发规范 / 场景设计 / 工作日志 / 部署手册 / 调研记录 |
| 适用场景 | 面板开发 / 生产制造 / 库存供应链 / 质量 / 审批 / 报表 / 部署 |
| 维护状态 | 生效 / 草案 / 调研基线 / 历史记录 / 归档 |
| 最后更新 | YYYY-MM-DD |
```

外部来源、测试环境和原始资料放在元信息表之后，使用引用块说明。

## 3. 标题层级

- `#`：文档标题，每个文件只能出现一次。
- `##`：主要章节。
- `###`：章节内主题。
- `####`：仅用于复杂主题的局部拆分。
- 不允许从 `##` 直接跳到 `####`。
- 新文档使用阿拉伯数字编号，例如 `## 1. 范围`、`### 1.1 约束`；历史文档的中文编号可保留，避免破坏既有章节引用。

## 4. 场景归类

文档必须归入以下一个主场景，并在 [文档中心](README.md) 登记：

1. 通用架构与 SDK。
2. 面板开发规范。
3. 生产制造。
4. 库存与供应链。
5. 质量与车间。
6. 审批与流程。
7. 报表。
8. 部署与运维。
9. 测试、问题与工作日志。

跨场景文档只选择一个主场景，其他场景通过链接引用，禁止复制全文。

## 5. 规范与日志边界

| 内容 | 存放位置 |
|---|---|
| 当前必须遵守的规则 | 开发规范或设计规范 |
| 某面板的目标结构 | 对应场景设计 |
| 实施过程、命令和验证结果 | 工作日志 |
| 可重复复现的问题 | `BUG总结.md` |
| 截图、DOM、抓包和 E2E 原始结果 | `docs/ref/` |
| 当前部署操作 | `docs/deploy/部署说明.md` |
| 特定环境部署复盘 | 标记为“历史记录”的部署日志 |

日志采用“日期 → 目标 → 改动 → 验证 → 遗留项”结构。Bug 采用“现象 → 根因 → 修复 → 验证 → 教训”结构。

## 6. 正文排版

- 段落之间保留一个空行，不使用连续多个空行制造间距。
- 无序列表统一使用 `-`；有序步骤使用 `1. 2. 3.`。
- 文件、命令、环境变量、接口和代码标识使用反引号。
- 命令块必须标注语言，如 `bash`、`powershell`、`sql`、`json`、`java`。
- 表格必须有表头和分隔行；单元格内容过长时改用列表，不强塞入宽表。
- 分隔线 `---` 只用于长文档主要章节之间，不在每个小节重复使用。
- 不使用 Emoji 表示验证状态；统一写“通过”“失败”“未验证”或使用 Markdown 任务框。

## 7. 链接与文件路径

- 文档间使用相对链接，文件路径使用仓库相对路径。
- 文档导航集中在 [文档中心](README.md)，其他文档不维护重复的全量索引。
- 源代码行号容易变化，规范中优先链接文件和函数名；调研日志可以保留当时行号。
- 图片和原始资料放入 `docs/ref/<场景>/`，不要把大体积取证文件放进规范目录。

## 8. 安全要求

- 禁止记录真实密码、Token、Cookie、私钥、数据库凭据和生产服务器身份信息。
- 示例凭据统一写为 `<用户名>`、`<密码>`、`<服务器IP>`、`<Token>`。
- 已失效但曾真实使用的凭据也必须打码，因为 Git 历史可能长期保留。
- 日志中的用户数据、客户数据和业务单号按排障所需的最小范围保留。

## 9. 状态与优先级

当文档内容冲突时，按以下优先级判断：

1. 标记为“生效”的开发规范和当前部署说明。
2. 当前代码、自动化测试和机器可读 Schema。
3. 场景设计和调研基线。
4. 工作日志与历史部署记录。
5. `docs/ref` 原始资料。

发现冲突时应修正规范并在日志中记录原因，不应在多份文档中分别修改同一规则。

## 10. 自动检查

在仓库根目录执行：

```bash
node tools/docs-audit.mjs
```

检查内容包括：UTF-8、BOM、文件尾换行、一级标题数量、标题跨级、内联字体样式、相对链接和文档中心归类。
